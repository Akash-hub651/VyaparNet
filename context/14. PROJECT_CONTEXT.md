## 1. PROJECT IDENTITY

### Vision

```
VyaparNet aims to become Bharat-first B2B commerce infrastructure,
connecting manufacturers, wholesalers, and retailers
across India through a unified, trusted, low-friction platform.
```

### Mission

```
Solve India-specific B2B procurement:
- Difficulty finding reliable suppliers
- Lack of price transparency
- Broken trust in transactions
- Operational inefficiency in ordering
- Discovery friction for Bharat buyers
```

### Core Principles

| Principle | What it means | Never compromise |
|-----------|--------------|------------------|
| **Bharat-first** | Built for low-end Android, 2GB RAM, 3G networks | Offline is not optional |
| **Mobile-first** | 70%+ users will access via mobile | No desktop-only features in MVP |
| **Low-friction onboarding** | OTP + business name = live in 60 seconds | No long forms at signup |
| **Trust-first commerce** | Verified sellers, GST, ratings, transparent pricing | Never skip seller verification |
| **Search-first UX** | 70% journeys start with search, not browsing | Homepage is search bar |
| **Operational simplicity** | Sellers focus on selling, not platform complexity | No complex dashboards for MVP |
| **Speed over beauty** | Page load < 2s, interaction < 150ms | No heavy animations |
| **Reliability over features** | Core flow works 100%, fancy features optional | Checkout path is sacred |

## 2. PRODUCT PHILOSOPHY

### How Product Decisions Are Made

```
DECISION HIERARCHY:
  1. Buyer needs (search, MOQ, price, trust signals)
  2. Seller needs (visibility, orders, payment, inventory)
  3. Platform needs (quality, safety, scalability)
  4. Nice-to-haves (analytics, AI, advanced features)

FEATURE PRIORITIZATION:
  - Must have: Blocks checkout or core flow
  - Should have: Significantly improves experience
  - Could have: Nice but not critical
  - Won't have: Phase 2+

RULE: "Does this help a buyer place an order?" → No? → Phase 2
```

### Product Principles

| Principle | Description |
|-----------|-------------|
| **Simplicity over feature overload** | One feature done well > 5 features half-baked |
| **Speed over animation** | Subtle micro-interactions only. No hero animations |
| **Usability over aesthetics** | Functional > beautiful. Clean > flashy |
| **Trust over everything** | Verified seller badge > fancy UI. GST > slick onboarding |
| **Low cognitive load** | Max 3 actions per screen. No decision fatigue |
| **Operational visibility** | Sellers see what matters (orders, stock, revenue) |
| **Hinglish-friendly** | "Search karein" not "Search for products". Conversational |
| **Minimal typing** | OTP auto-fill, recent picks, quick selects. Voice search |
| **Predictable patterns** | Same navigation, same buttons, same colors everywhere |

## 3. TECHNICAL PHILOSOPHY

### Engineering Principles

```
MONOLITH FIRST
  - Single NestJS backend, single Next.js frontend
  - Modular monolith: clean boundaries, no tight coupling
  - Extract to microservices ONLY when metrics justify it

DB INTEGRITY FIRST
  - Schema correctness > speed of development
  - Migrations: forward-compatible, zero-downtime
  - Every state change: audit log + immutability
  - No raw SQL (always use Prisma ORM)

TYPED SYSTEMS ONLY
  - TypeScript everywhere (strict mode)
  - No "any" (use unknown + validate)
  - DTO validation on every API boundary
  - Shared types in packages/types (no duplication)

ASYNC WHERE POSSIBLE
  - Notifications, analytics, emails: always async (queue)
  - Search reindex: async (BullMQ worker)
  - Image processing: async (worker)
  - Sync path: auth, CRUD, order placement (fast)

GRACEFUL DEGRADATION
  - If search suggestions fail: basic search still works
  - If notifications fail: core commerce continues
  - If analytics fail: skip (no impact on orders)
  - If Redis down: fallback to DB (slower but correct)

OBSERVABILITY MANDATORY
  - Every critical flow: metrics + logs + traces
  - Every error: logged with context + trace_id
  - Every state change: audit log
  - Every deployment: health check + smoke test

NO PREMATURE MICROSERVICES
  - Phase 1: Monolith (6-12 months)
  - Phase 2: Extract heavy modules (notifications, search)
  - Phase 3: Microservices (if team > 8 engineers)
```

### What MUST NEVER Happen

| Anti-Pattern | Why | Prevention |
|-------------|-----|-----------|
| **Direct DB from frontend** | Security, coupling, no validation | API-only access. Never expose DB |
| **Untyped APIs** | Runtime errors, broken contracts | DTOs + validation on every endpoint |
| **Hidden failures** | Silent bugs, data corruption | Alert on every failure. Log everything |
| **Blocking checkout for non-critical services** | Lost revenue | Degraded mode: checkout works even if analytics/search fail |
| **Business logic in frontend** | Security, duplication, inconsistency | Frontend = presentation only. Logic in backend |
| **Silent queue failures** | Lost jobs, data inconsistency | Monitor queue depth. Alert on failures. DLQ mandatory |
| **Hardcoded secrets** | Security breach | Env vars only. Secret scan in CI |
| **Skipping migrations** | Data inconsistency | Every schema change: migration + rollback |
| **No audit log on state changes** | Untraceable bugs, compliance issues | Every UPDATE/DELETE: audit log |
| **Frontend validation only** | Bypassable, insecure | Always validate server-side |

## 11. RUNTIME GUARANTEES

> **What the system must always guarantee, even under failure.**

| Guarantee | How | Fallback |
|-----------|-----|----------|
| **No oversell** | Optimistic locking (version) + Redis lock | Block order if stock unavailable |
| **Idempotent payments** | Idempotency key in Redis (TTL 24h) | Return cached response |
| **Checkout path survives** | Core commerce: search, product, cart, order, COD | Degraded mode for non-essential services |
| **Audit logs immutable** | Append-only, no UPDATE/DELETE | Cannot be modified, only read |
| **Retry-safe queues** | Idempotency keys, BullMQ retries, DLQ | Manual replay from DLQ |
| **Graceful degradation** | Non-essential services degrade: search suggestions, analytics, notifications | Core commerce continues |
| **Graceful shutdown** | SIGTERM handler: drain, close DB/Redis, exit cleanly | Kill after 30s timeout |
| **Zero-downtime deploy** | Blue-green, health check before traffic | Rollback manually if health check fails |
| **No data loss on deploy** | Forward-compatible migrations, immutable logs | Point-in-time recovery (WAL) |
| **Consistent state** | ACID transactions for order + inventory | Rollback transaction on failure |
| **Secure secrets** | Env vars only, never in code | Secret scan in CI (gitleaks) |
| **Valid API contracts** | DTO validation (Zod / class-validator) | Return 400, log validation error |
| **Rate limiting** | Per-IP, per-user, per-endpoint | Block with 429 + Retry-After |

## 12. OPERATIONAL PHILOSOPHY

### How We Operate

```
ROLLOUT-FIRST MINDSET:
  - Every deployment must have a rollback plan
  - Health check before traffic
  - Can roll back within 5 minutes (Docker image switch)
  - Rollback > fix forward (in production)

OBSERVABILITY-FIRST:
  - Monitor everything (not just errors)
  - Alert on symptoms, not causes
  - Every critical flow has metrics + logs + traces
  - Dashboards for all teams (not just on-call)

DEPLOY SAFELY:
  - No Friday deploys after 4 PM IST
  - Feature flags for risky changes
  - Progressive rollout: 5% -> 25% -> 50% -> 100%
  - Ship small, ship often (daily possible)
  - Branch protection: main, develop, feature/*
  - CI/CD gates: lint, test, typecheck, security scan, build

FREEZE WINDOWS:
  - No deploy Friday 4 PM - Monday 9 AM IST
  - No deploy during festivals / sales (Diwali, Black Friday)
  - Hotfix: deploy anytime (but verify + monitor)

INCIDENT OWNERSHIP:
  - Every system has an owner (person, not team)
  - Escalation: primary -> secondary -> CTO (15 min response)
  - Blameless postmortem within 24 hours (SEV-1, SEV-2)
  - Runbook for every known failure (pre-scripted response)
```

## 13. SECURITY PHILOSOPHY

| Principle | What it means | How |
|-----------|--------------|-----|
| **Least privilege** | Minimum permissions needed | RBAC roles: buyer, seller, admin |
| **Zero trust between modules** | Validate all inputs, no implicit trust | DTO validation on every boundary |
| **No secrets in code** | Never commit API keys, passwords | Env vars only, secret scan CI |
| **Validate all input** | Never trust user data | Server-side validation (Zod) |
| **Audit every state change** | Log who did what, when | Immutable audit log |
| **Rate limit everything** | Prevent abuse | Per-IP, per-user, per-endpoint |
| **Encrypt in transit** | TLS 1.3 everywhere | Cloudflare + AWS ACM |
| **Encrypt at rest** | DB, backups, storage | AES-256 (managed) |
| **Principle of least knowledge** | Frontend knows as little as possible | API-only access, no DB |
| **Fail safely** | Security failures block, not bypass | Default deny |

## 16. SCALING PHILOSOPHY

```
SCALE ONLY WHEN METRICS JUSTIFY IT!

Triggers:
  DB CPU > 80%, queue depth > 10K, latency p95 > 500ms
  THEN optimize -> add capacity
  NOT before.

READ REPLICAS:
  Trigger: Read-heavy ops (analytics, search, dashboard)
  When: DB CPU > 60%
  How: Add read replica, route read queries

CDN:
  Trigger: Static assets slow, high bandwidth cost
  When: Always (enabled from day 1)
  How: Cloudflare, image optimization

WORKERS:
  Trigger: Queue depth > 1K for 5 min
  When: Always monitoring
  How: Scale horizontally (more containers)

API SERVERS:
  Trigger: CPU > 70% for 5 min
  When: After DB is optimized
  How: Horizontal scale (more containers)

REDIS:
  Trigger: Memory > 85%
  When: Cache eviction rate high
  How: Bigger instance or cluster

OPENSEARCH (Phase 2):
  Trigger: Search > 100 req/sec
  When: PostgreSQL GIN insufficient
  How: Add OpenSearch, sync data

KAFKA (Phase 2+):
  Trigger: Events > 100K/day
  When: BullMQ insufficient
  How: Add Kafka cluster

ECS/K8s (Phase 2+):
  Trigger: Team > 5, need auto-scaling
  When: Docker Compose manual scaling painful
  How: Migrate to ECS/K8s
```

## 22. ANTI-PATTERNS REGISTRY

> **Patterns that MUST NEVER be used. Checked in code review.**

| Anti-Pattern | Why | Prevention |
|-------------|-----|-----------|
| **Premature scaling** | Optimize before proving need | Measure, profile, then optimize. No "just in case" |
| **Feature explosion** | Bloat kills focus | Strict MVP cutline. "No" default for new features |
| **Infra theatre** | Complex infra doesn't ship product | Docker Compose is fine. Don't add K8s until needed |
| **Hidden coupling** | Dependencies that aren't visible | Modular monolith, no shared state, explicit imports |
| **Giant PRs** | Unreviewable, risky | < 400 lines per PR. Split into smaller PRs |
| **Skipping tests** | Regression, broken flows | CI gate: tests must pass. Code coverage gate |
| **Frontend business logic** | Security, duplication | Backend = source of truth. Frontend = presentation only |
| **No error handling** | Silent failures, hidden bugs | Try/catch everywhere. Log errors. User-friendly messages |
| **Hardcoding secrets** | Security breach | Env vars only. Secret scan in CI |
| **Skipping migrations** | Data inconsistency | Every schema change: migration + rollback |
| **No audit trail** | Untraceable, compliance risk | Every mutation: audit log |
| **Blocking checkout for analytics** | Lost revenue | Degraded mode: core path never blocked |
| **Ignoring performance** | Slow product = churn | Performance budgets, monitoring, alerts |
| **Not documenting decisions** | Context loss, repeated debates | DDR for every major decision |
| **Over-optimizing** | Diminishing returns | "Good enough" > "Perfect". Ship and iterate |

ROTATION RULES:
