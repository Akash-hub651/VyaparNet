## 1. RUNTIME PHILOSOPHY

### 1.1 Core Principles

```
FAIL SAFELY
  Every failure mode returns a safe, known state.
  Never leave transactions in limbo.

GRACEFUL DEGRADATION
  Core commerce survives even when non-essential services fail.

ASYNC WHERE POSSIBLE
  Non-critical paths are always async (notifications, analytics, emails).

EVENT-DRIVEN SIDE EFFECTS
  All side effects (email, analytics, search reindex) are offloaded to events.

STATELESS APIS
  API servers do not store local state between requests.
  All state is in PostgreSQL or Redis.

QUEUE-FIRST HEAVY PROCESSING
  Heavy processing (image processing, CSV import, report generation) runs in workers.

SCALE HORIZONTALLY
  Add more containers (not bigger machines) to handle load.

PROTECT DB FIRST
  Database is the most critical and hardest-to-scale resource.
  All optimizations prioritize DB health.

OBSERVABILITY MANDATORY
  Every critical flow emits metrics, logs, and traces.

RETRY SAFELY
  Retries use exponential backoff with jitter.
  Never retry blindly.

IMMUTABLE AUDIT LOGS
  All audit logs are append-only and immutable.

UTC EVERYWHERE
  All timestamps in UTC. Client converts to local timezone.
```

### 1.2 System Non-Goals (Phase 1)

```
❌ NOT microservices (MVP: modular monolith)
❌ NOT multi-region (single region: Mumbai ap-south-1)
❌ NOT Kubernetes (MVP: Docker Compose on EC2/VM)
❌ NOT Kafka (BullMQ + PostgreSQL sufficient)
❌ NOT OpenSearch (PostgreSQL GIN sufficient)
❌ NOT real-time WebSocket (polling for MVP)
❌ NOT multi-tenant (single business per user)
```

### 1.3 Runtime Mindset

```
SYSTEM THINKING:
  Build for failure — not for the happy path.
  Monitor everything — not just error rates.
  Plan for 3AM incidents — not 12PM demos.
  Optimize for debugging — not for beauty.
  Prefer simplicity — until complexity is justified by scale.

COST AWARENESS:
  EveryChoice * $ = engineering decision.
  Log everything — but not everything needs to be stored forever.
  Scaled infrastructure costs more than development time.
  Unused resources = wasted money. Auto-shutdown non-prod environments.
```

### 1.4 Runtime Capacity Planning

MVP sizing targets for scaling decisions:

| Resource | MVP Target | Critical Threshold | Action |
|----------|-----------|-------------------|--------|
| **Concurrent users** | 500 active | 1,000 | Scale API containers |
| **Orders / min** | 50 | 100 | Add workers, scale DB |
| **Queue jobs / min** | 500 | 1,000 | Scale workers, add Redis |
| **DB TPS** | 500 | 800 | Add read replicas |
| **Redis memory** | 10GB (80%) | 16GB (85%) | Scale up instance |
| **API RPS** | 100 | 200 | Scale API containers |
| **File uploads / hr** | 500 | 1,000 | Add S3/R2 throughput |
| **Concurrent sessions** | 10,000 | 20,000 | Scale Redis |

```
GROWTH RULES:
  - Monitor weekly: actual vs target
  - Alert: 80% of any target
  - Scale BEFORE hitting limit
  - Document capacity decisions in DDR
```

### 1.5 API Timeout Governance

Global timeout standards for resilience:

| Operation | Timeout | Max Retries | Fallback |
|-----------|---------|-------------|----------|
| **API request** | 10s | 1 (total 20s) | Return 503 |
| **DB query** | 5s | 2 (exponential) | Return empty/error |
| **Redis read** | 500ms | 1 | Read from DB |
| **Redis write** | 500ms | 1 | Skip cache write |
| **Webhook delivery** | 15s | 3 (2s, 4s, 8s) | Queue for retry |
| **Worker job** | Queue-specific | Varies | DLQ |
| **Payment gateway** | 30s | 0 | Queue for review |
| **Image upload** | 60s | 0 | Fail with error |
| **Search query** | 2s | 0 | Return empty results |
| **Auth (JWT verify)** | 100ms | - | Reject (401) |

```
TIMEOUT GOVERNANCE:
  - All timeouts defined in config (not hardcoded)
  - Alert: p95 latency > 80% of timeout
  - Circuit breaker: 5 consecutive timeouts = open
  - Graceful: Always return meaningful error to user
```

### 1.6 Idempotency Governance

Critical for payments, orders, inventory:

| Operation | Idempotency Key | TTL | Conflict Behavior |
|-----------|---------------|-----|-------------------|
| **Payment init** | `idempotency:{userId}:{txnId}` | 24h | Return existing payment |
| **Order creation** | `idempotency:{userId}:{cartId}` | 1h | Return existing order |
| **Inventory reserve** | `idempotency:{productId}:{qty}:{userId}` | 900s | Return existing reservation |
| **Webhook delivery** | `idempotency:{webhookId}:{eventId}` | 24h | Return 200 OK |
| **Refund** | `idempotency:{paymentId}:refund:{amount}` | 30d | Return existing refund |
| **Product create** | `idempotency:{sellerId}:{sku}` | 24h | Return 409 conflict |

```
IDEMPOTENCY RULES:
  - Client generates UUID as idempotency key
  - Server stores: key → response → TTL
  - Duplicate key: return cached response (HTTP 200 or 409)
  - Key collision (different request, same key): reject 400
  - TTL expiration: re-process normally
  - Keys: hash(clientId + action + resource)
  - Storage: Redis (TTL: 24h default)
  - Replay: check idempotency key before processing
```

## 2. ENVIRONMENT STRATEGY

### 2.1 Environment Matrix

| Environment | Purpose | Data | Uptime SLA | Access |
|-------------|---------|------|------------|--------|
| **local** | Developer machine | Synthetic / dev clone | N/A | Individual dev |
| **staging** | QA, feature testing | Anonymized prod snapshot | 95% | Team only |
| **preprod** | Load testing, prod rehearsal | Prod-like (1 week old) | 99% | Team only |
| **production** | Live users | Real | 99.9% | Restricted |

### 2.2 Environment Parity Rules

```
PARITY LEVELS:
  staging  ≈  production  (same Docker images, same env vars)
  preprod  ≈  production  (same DB size, same worker count)

ENVIRONMENT DIFFERENCES:
  staging:    smaller instances, some features disabled
  preprod:    same size as prod, test payments (sandbox)
  production: full scale, real payments

FORBIDDEN: Production-only behavior
  ✗ Code that only exists in production
  ✗ Data models that differ per environment
  ✗ Feature flags that work differently in prod
  ✗ Hardcoded configs per environment (use env vars)
```

### 2.3 Configuration Strategy

```
CONFIG MANAGEMENT:
  - All configs via environment variables (12-factor app)
  - No config files in Docker images
  - Secrets: env vars (MVP) → HashiCorp Vault / AWS Secrets Manager (Phase 2)
  - Feature flags: env var (MVP) → LaunchDarkly / Unleash (Phase 2)

ENV VAR CATEGORIES:
  DATABASE_URL          (PostgreSQL connection string)
  REDIS_URL             (Redis connection string)
  JWT_SECRET            (JWT signing key)
  RAZORPAY_KEY          (Payment gateway credentials)
  S3_BUCKET             (Object storage)
  SMTP_HOST             (Email provider)
  SMS_API_KEY           (MSG91 / Twilio)
```

DB (sync):
  NestJS API → PostgreSQL (read/write)
  NestJS Worker → PostgreSQL (read/write)

CACHE (sync):
  Next.js → Redis (read)
  NestJS API → Redis (read/write)

```
vyaparnet/

  │   │   ├── src/
  │   │   ├── next.config.js
  │   │   └── Dockerfile
  │   ├── api/                  # NestJS (API server)
  │   │   ├── src/
  │   │   ├── main.ts
  │   │   └── Dockerfile
  │   └── worker/               # NestJS (job workers)
  │       ├── src/
  │       └── Dockerfile
  │
  ├── packages/
  │   ├── ui/                   # Shadcn/Tailwind components
  │   ├── database/             # Prisma schema + migrations
  │   ├── types/                # Shared TypeScript types
  │   └── config/               # Shared config (eslint, tsconfig)
  │
  ├── infra/
  │   ├── docker-compose.yml    # Local dev
  │   ├── docker-compose.prod.yml # Production
  │   └── nginx/                # Nginx config
  │
  ├── docs/                     # Architecture docs (frozen)
  │   └── ddr/                  # Design Decision Records
  │
  ├── docker-compose.yml
  ├── pnpm-workspace.yaml
  └── turbo.json
```

### 4.2 Deployment Boundaries

```
WEB (Next.js):
  - Builds as static + server-side
  - Docker: Next.js runtime inside container
  - CDN: Static assets on Cloudflare
  - Deploy: New container per release

API (NestJS):
  - Builds as Node.js app
  - Docker: NestJS runtime inside container
  - No static files served from API
  - Deploy: New container per release

WORKER (NestJS):
  - Same codebase as API (shared packages/database)
  - Different entry point (worker.ts vs main.ts)
  - Docker: Different CMD in Dockerfile
  - Deploy: New container per release (separate from API)

DATABASE (PostgreSQL):
  - Managed database (AWS RDS / GCP Cloud SQL / DigitalOcean)
  - NOT deployed as part of application
  - Migrated separately (prisma migrate deploy)

REDIS (Cache + Queues):
  - Managed Redis (AWS ElastiCache / GCP Memorystore)
  - One instance for both cache AND queues (MVP)
  - Future: separate instances for cache vs queues

OBJECT STORAGE (S3/R2):
  - Cloudflare R2 (cheaper egress) or AWS S3
  - Separate bucket per environment
```

### 4.3 Shared Code Strategy

```
PACKAGES/
  database/
    - Prisma schema (single source of truth)
    - Migration scripts
    - Seed scripts
    - Published to npm (private)

  ui/
    - React components (Shadcn + Tailwind)
    - Shared across web + admin
    - Built before dependent apps
    - Published to npm (private)

BUILD ORDER (Turborepo):
  1. packages/config      (no deps)
  2. packages/types       (depends on config)
  3. packages/database    (depends on types)
  4. packages/ui          (depends on types)
  5. apps/worker          (depends on database, types)
  6. apps/api             (depends on database, types)
  7. apps/web             (depends on ui, types)
```

## 5. CONTAINERIZATION STRATEGY

### 5.1 Docker Standards

```
BASE IMAGE:
  - Node.js 20 Alpine (lightweight, 180MB base)
  - No apt-get in production (pre-built only)

MULTI-STAGE BUILD:
  Stage 1: deps    - Install dependencies
  Stage 2: build   - Compile TypeScript, build Next.js
  Stage 3: prd     - Copy only dist/node_modules, run

IMAGE SIZE LIMIT:
  - web: < 300MB
  - api: < 200MB
  - worker: < 200MB

SECURITY:
  - Non-root user (node, uid=1000)
  - Read-only root filesystem
  - No shell (use distroless or busybox)
  - Healthcheck defined
```

### 5.2 Dockerfile Template (API)

```dockerfile
# Stage 1: Dependencies
FROM node:20-alpine AS deps
WORKDIR /app
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml turbo.json ./
COPY apps/api/package.json ./apps/api/package.json
COPY packages/database/package.json ./packages/database/package.json
COPY packages/types/package.json ./packages/types/package.json
RUN corepack enable && pnpm install --frozen-lockfile

# Stage 2: Build
FROM node:20-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN pnpm --filter=api build
RUN pnpm --filter=api deploy --prod ./deploy

# Stage 3: Production
FROM node:20-alpine AS production
WORKDIR /app
RUN addgroup -g 1001 -S nodejs && adduser -S nodejs -u 1001
COPY --from=builder --chown=nodejs:nodejs /app/deploy .
USER nodejs
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD curl -f http://localhost:3000/health || exit 1
CMD ["node", "main.js"]
```

### 5.3 Healthcheck & Graceful Shutdown

```
HEALTHCHECK ENDPOINTS:
  /health     → HTTP 200 (liveness: is process running?)
  /ready      → HTTP 200 (readiness: can serve traffic?)
              → checks: DB connection, Redis connection

GRACEFUL SHUTDOWN:
  1. Receive SIGTERM (or SIGINT)
  2. Stop accepting new requests (load balancer removes from pool)
  3. Wait for in-flight requests to complete (max 30s)
  4. Close DB connections
  5. Close Redis connections
  6. Exit process

TIMEOUTS:
  - Graceful shutdown: 30 seconds
  - In-flight requests: max 30s to complete
  - Connections close: 5 seconds
```

### 5.4 Container Immutability

```
RULES:
  - Container image is built once, deployed everywhere (staging → preprod → prod)
  - No runtime code changes in containers
  - No volume mounts for code (only for logs/temp)
  - Config via env vars only (no config files baked in)
  - Tag: semantic version (e.g., api:1.2.3)
```

## 6. RUNTIME NETWORKING ARCHITECTURE

### 6.1 Network Layers

```
PUBLIC LAYER (Internet-facing):
  Cloudflare CDN
    ↓
  AWS ALB / Nginx (Load Balancer)
    ↓
  [Public Subnet]

PRIVATE LAYER (VPC-internal):
  [Private Subnet]
    ├── Next.js containers
    ├── NestJS API containers
    ├── NestJS Worker containers
    ├── PostgreSQL (managed, private subnet)
    └── Redis (managed, private subnet)

FORBIDDEN: Direct internet access from private layer.
  - Workers pull from S3 via VPC endpoint (not public internet)
  - API calls Razorpay via NAT gateway (outbound only)
```

### 6.2 Ingress Rules

| Source | Target | Port | Protocol | Purpose |
|--------|--------|------|------------|---------|
| Internet | ALB | 443 | HTTPS | Buyer PWA |
| Internet | ALB | 443 | HTTPS | Admin dashboard |
| ALB | Next.js | 3000 | HTTP | Web app |
| ALB | NestJS API | 3000 | HTTP | API requests |
| Internal | NestJS Worker | none | Queue | BullMQ (Redis) |
| VPC | PostgreSQL | 5432 | TCP | DB connections |
| VPC | Redis | 6379 | TCP | Cache & queues |

### 6.3 Internal Service Communication

```
WEB → API:        HTTPS via ALB (public route)
API → DB:         Direct TCP (private subnet)
API → Redis:      Direct TCP (private subnet)
API → S3:         HTTPS via VPC Endpoint (private)
Worker → API:     NOT directly (only via DB + Redis)
Worker → DB:      Same as API
Worker → Redis:   Same as API
```

### 6.4 TLS Termination

```
TLS OFFLOADING:
  - TLS terminates at Cloudflare (Edge) → HTTP between Cloudflare and ALB
  - OR: TLS terminates at ALB → HTTP between ALB and containers
  - Containers see HTTP only (no TLS in app code)

CERTIFICATE MANAGEMENT:
  - Cloudflare: Auto-managed (free TLS)
  - ALB: AWS ACM certificate
  - Renewal: Automatic
```

## 7. CDN + ASSET DELIVERY STRATEGY

### 7.1 CDN Architecture (Cloudflare)

```
TRAFFIC FLOW:
  User → Cloudflare (DNS + CDN + WAF)
    → Cloudflare Edge Cache (static assets)
      → AWS ALB (dynamic requests)
        → Next.js / NestJS containers

CACHED AT CLOUDFLARE EDGE:
  - Static JS/CSS bundles
  - Product images (after first request)
  - Logo, icons, favicon

PASSTHROUGH (NO CACHE):
  - API requests (/api/*)
  - Auth endpoints (/auth/*)
  - Webhooks (/webhooks/*)
```

### 7.2 Static Asset Cache Rules

| Asset Type | Cache Duration | Cache Key | Busting |
|------------|---------------|-----------|---------|
| JS/CSS bundles | 1 year | URL + build hash | Build hash in filename |
| Product images | 7 days | URL | Version query param |
| Logo/icons | 1 year | URL | Version query param |
| API responses | 0 (no cache) | - | - |

### 7.3 Product Image Pipeline

```
UPLOAD FLOW:
  Seller uploads image (JPG/PNG, max 10MB)
    → API validates (format, size, dimensions)
    → Compress + convert to WebP (quality 80)
    → Resize to variants: thumb (200x200), medium (400x400), large (800x800)
    → Auto-center crop (1:1 ratio)
    → Upload to S3/R2 with cache headers
    → Store URL in PostgreSQL

CDN CACHING:
  - Images served via Cloudflare R2 / S3 with signed URLs
  - Cache-Control: public, max-age=604800 (7 days)
  - Background cleanup: old variants purged after 30 days

OPTIMIZATION:
  - WebP with JPEG fallback
  - Lazy loading with blurhash placeholder
  - srcset for responsive images
```

### 7.4 Bharat Optimization

```
MOBILE-FIRST DELIVERY:
  - Images: Serve 200px thumbs on mobile (not 800px)
  - JS bundles: Next.js code splitting, lazy load routes
  - Cache aggressively on client (service worker)
  - Use Cloudflare's India PoPs (Mumbai, Delhi, Bangalore)

LOW-BANDWIDTH USERS:
  - Option to disable auto-play images (data saver mode)
  - Compressed JS bundles (< 200KB initial)
  - Fallback to 2G: degraded search, no images
```

## 8. DATABASE RUNTIME STRATEGY

### 8.1 PostgreSQL Architecture

```
PHASE 1 (MVP):
  - Single PostgreSQL instance (managed: AWS RDS / DigitalOcean / Supabase)
  - Read + Write on same instance
  - Connection pool: pgBouncer or Prisma built-in pooler
  - Size: Start small (db.t3.micro), scale up as needed

PHASE 2 (Growth):
  - Read replicas: 1-2 replicas for read-heavy ops
  - Separate: analytics reads (read replica)
  - Connection pooler: pgBouncer (mandatory)

PHASE 3 (Scale):
  - Consider: Table partitioning (orders, logs)
  - Consider: Connection pooling (PgBouncer mandatory)
```

### 8.2 Connection Management

| Parameter | Value | Reason |
|-----------|-------|--------|
| Max connections | 100 (DB) | AWS RDS default |
| Prisma pool size | 20 | Per app container |
| Connection timeout | 5s | Fail fast |
| Idle timeout | 10min | Reuse connections |
| Connection max | 100 | Per DB |

### 8.3 Connection Pool Strategy

```
RULE: Never create connections per-request. Always use pool.

Prisma Connection Pool (per container):
  min: 2 connections
  max: 20 connections
  idleTimeout: 10 minutes
  acquireTimeout: 5 seconds

PgBouncer (Phase 2):
  mode: transaction pooling
  max_client_conn: 1000
  max_db_connections: 100
  reserve_pool: 5
```

### 8.4 Database Runtime Failure Handling

```
DB UNAVAILABLE:
  1. API returns 503 with retry-after header
  2. Queue workers pause (BullMQ handles this automatically)
  3. Health check fails → container marked unhealthy
  4. Load balancer routes to healthy containers only

DB SLOW:
  1. p95 query time > 200ms → alert WARNING
  2. p95 > 1000ms → alert CRITICAL
  3. Enable query logging (slow_query_log)
  4. Review: missing indexes, N+1 queries

DB CONNECTION EXHAUSTION:
  1. Monitor: active_connections / max_connections
  2. Alert at >80%
  3. Immediate: Restart idle containers (releases connections)
  4. Short-term: Scale DB up (bigger instance)
  5. Long-term: Add read replicas
```

### 8.5 Migration Strategy at Runtime

```
ZERO-DOWNTIME MIGRATIONS:
  1. Migrations run BEFORE new code deploys
  2. Forward-compatible migrations only (no breaking changes)
  3. Old code must work with new schema
  4. Backward-compatible schema (old columns kept until confirmed safe to remove)

MIGRATION PROCESS:
  1. Prisma migrate deploy (runs in CI/CD before app start)
  2. Verify: health check passes before routing traffic
  3. Rollback: Down migration (tested before deploy)
  4. Emergency: Revert to old Docker image (schema is forward-compatible)
```

### 8.6 Backup Strategy

```
AUTOMATED BACKUPS:
  - Frequency: Daily (managed by cloud provider)
  - Retention: 7 days (daily), 30 days (weekly), 90 days (monthly)
  - Type: Full snapshot + WAL (Write-Ahead Log) continuous archiving
  - Storage: Cross-region (different availability zone)

MANUAL BACKUPS:
  - Before major releases
  - Before schema migrations
  - Named: pre-release-[version]-[date]

RESTORE TESTING:
  - Monthly: Restore backup to staging (automated)
  - Verify: data integrity check
  - RTO: < 4 hours (acceptable for MVP)
  - RPO: < 24 hours (daily backups)

POINT-IN-TIME RECOVERY:
  - WAL archiving → restore to any point within 7 days
  - Use case: Accidental DELETE, data corruption
```

## 9. REDIS RUNTIME STRATEGY

### 9.1 Redis Architecture

```
PHASE 1 (MVP):
  - Single Redis instance (managed: AWS ElastiCache / DigitalOcean / Upstash)
  - Shared use: Sessions + Cache + Queues + Rate Limiting
  - Risk: Single point of failure for non-critical features

PHASE 2 (Growth):
  - Separate: Sessions (persistent) vs Queues (ephemeral)
  - Redis Cluster (if memory > 16GB)
  - Redis Sentinel (for high availability)

PHASE 3 (Scale):
  - Separate Redis per concern:
    - sessions-cache (persistent, smaller)
    - bullmq-queues (ephemeral, larger)
    - rate-limiter (ephemeral, fast)
```

### 9.2 Redis Use Cases

| Use Case | Key Pattern | TTL | Max Size |
|----------|------------|-----|----------|
| **Sessions** | `session:{userId}` | 7 days | 5MB per user |
| **OTP** | `otp:{phone}` | 5 min | - |
| **Rate Limits** | `ratelimit:{ip}` | 1 min | - |
| **Product Cache** | `product:{id}` | 5 min | - |
| **Cart** | `cart:{userId}` | 24 hours | - |
| **Search Cache** | `search:{hash}` | 5 min | - |
| **BullMQ Queues** | `bullmq:{queue}:{jobId}` | Varies | - |
| **Distributed Lock** | `lock:{resource}` | 30s | - |

### 9.3 Redis Failure Handling

```
REDIS UNAVAILABLE:
  Cache:     Fallback to DB (read, no write)
  Sessions:  Force re-login (not ideal, but acceptable)
  Queues:    API queues jobs for retry (BullMQ handles this)
  Rate Limit: Gracefully allow (risk: temporary no rate limiting)

REDIS SLOW (>100ms response):
  1. Alert: WARNING
  2. Investigate: Large keys, memory pressure, eviction
  3. Fallback: Skip cache, serve from DB (slower but functional)

REDIS MEMORY >85%:
  1. Evict analytics cache first (least important)
  2. Evict search cache (acceptable to miss)
  3. Alert: CRITICAL
  4. Scale up Redis instance
```

### 9.4 Redis Persistence (MVP vs Production)

```
MVP:
  - No Redis persistence (acceptable: cache + sessions rebuild)
  - RDB snapshots (managed by cloud provider)

PRODUCTION:
  - AOF (Append-Only File) + RDB
  - AOF everysec (balance between performance and safety)
  - RDB snapshot every 15 minutes (backup)
```

## 10. QUEUE RUNTIME ARCHITECTURE

### 10.1 Queue Topology (BullMQ)

```
BULLMQ ARCHITECTURE:

  API Server
     |
     | POST /api/orders
     |   -> Queue 'payments' (critical)
     |   -> Queue 'notifications' (medium)
     |   -> Queue 'search-index' (low)
     |   -> Queue 'analytics' (background)
     |
     v
  Redis (Queue Storage)
     |
     | BullMQ Workers (NestJS)
     |   -> payments: 2 workers
     |   -> notifications: 2 workers
     |   -> search-index: 1 worker
     |   -> analytics: 1 worker
```

### 10.2 Queue Separation & Priorities

| Queue | Priority | Purpose | Workers | SLA |
|-------|----------|---------|---------|-----|
| **payments** | Critical(1) | Payment processing | 2 | < 1s |
| **inventory** | Critical(2) | Stock reservation | 2 | < 1s |
| **orders** | High(3) | Order confirmation | 2 | < 2s |
| **notifications** | Medium(5) | Email, SMS, push | 2 | < 5s |
| **search-index** | Low(7) | Search reindexing | 1 | < 5min |
| **analytics** | Low(8) | Event collection | 1 | < 60s |
| **email** | Low(9) | Batch emails | 1 | < 30s |

### 10.3 Retry & Backoff Strategy

```
RETRY CONFIG (per queue):
  payments:    max 3 retries, backoff: 2s, 4s, 8s
  inventory:   max 3 retries, backoff: 100ms, 200ms, 400ms
  orders:      max 5 retries, backoff: 2s, 4s, 8s, 16s, 32s
  notifications: max 3 retries, backoff: 5s, 10s, 20s
  search-index: max 3 retries, backoff: 30s, 60s, 120s
  analytics:   no retries (fire-and-forget)

STALLED JOB DETECTION:
  - Timeout: 30s (critical), 60s (default), 300s (background)
  - Action: Kill + Retry -> DLQ if still fails

DEAD LETTER QUEUE (DLQ):
  - Max retries reached -> Move to DLQ
  - Manual review required
  - Alert: Slack + Email
  - Retry: Re-queue with new idempotency key (after review)
```

### 10.4 Queue Monitoring

```
METRICS:
  - queue_depth (per queue) — gauge
  - queue_processing_time — histogram
  - queue_failures (per queue) — counter
  - queue_retries — counter
  - worker_heartbeat — health check

ALERTS:
  - queue_depth > 1000: WARNING (scale up workers)
  - queue_depth > 5000: CRITICAL (investigate bottleneck)
  - processing_time > SLA: WARNING
```

### 10.5 Queue Failure & Recovery

```
REDIS (QUEUE) DOWN:
  - New jobs: Queue in memory (BullMQ in-memory queue)
  - Existing jobs: Lost (redis is ephemeral for MVP)
  - API: Returns 503 (queue unavailable), client retries later

WORKER CRASH:
  - Job retried by BullMQ (idempotency key prevents duplicate)
  - Alert: "Worker [n] crashed 3 times in 5 minutes"
  - If > 5 crashes in 10 min: Alert OPS

STALLED JOBS:
  - BullMQ moves stalled job to DLQ after timeout
  - Manual review -> Retry or mark as failed
```

## 11. RUNTIME SCALING STRATEGY

### 11.1 Horizontal Scaling (Primary Strategy)

```
API SERVERS:
  Load: CPU > 70% for 5 min
  Action: Add more API containers (auto-scaling)
  Max: 10 containers (Phase 1)

WORKERS:
  Load: queue_depth > 1000 for 5 min
  Action: Add more worker containers per queue type
  Max: 5 per queue type (Phase 1)

WEB SERVERS (Next.js):
  Load: CPU > 70% for 5 min
  Action: Add more Next.js containers
  Max: 5 containers (Phase 1)
```

### 11.2 Vertical Scaling (Backup Strategy)

```
DB:
  Load: CPU > 80% for 10 min
  Action: Scale up instance size (db.t3.medium -> db.t3.large)
  Then: Add read replicas

REDIS:
  Load: Memory > 85%
  Action: Scale up instance size or add cluster nodes
```

### 11.3 Autoscaling Rules

| Resource | Trigger | Action | Min | Max |
|----------|---------|--------|-----|-----|
| API containers | CPU > 70% for 5min | +1 container | 2 | 10 |
| API containers | CPU < 30% for 10min | -1 container | 2 | 10 |
| Workers | queue_depth > 1000 | +1 worker per queue | 1 | 5 |
| Workers | queue_depth < 100 | -1 worker per queue | 1 | 5 |
| DB | CPU > 80% | Scale up instance | 1 | - |

### 11.4 DB-First Protection

```
RULE: Scale API/workers AFTER scaling DB.

WHY:
  - Adding more API containers -> more DB connections -> DB exhaustion
  - Solution: Add read replicas FIRST, then scale API

SEQUENCE:
  1. Monitor DB CPU / connections
  2. If DB near limits: SCALE DB (bigger instance + read replicas)
  3. Then: Scale API containers
  4. Then: Scale workers per queue depth
```

### 11.5 Load Balancer Configuration

```
ALB (Application Load Balancer):
  - Health check: /health (HTTP 200)
  - Interval: 30 seconds
  - Timeout: 5 seconds
  - Unhealthy threshold: 3 consecutive failures
  - Healthy threshold: 2 consecutive successes
  - Deregistration delay: 30 seconds (drain in-flight requests)

STICKINESS: None (all requests stateless)

SESSION MANAGEMENT:
  - Sessions stored in Redis (not in container memory)
  - Load balancer does not need session stickiness
```

## 13. RUNTIME FAILURE HANDLING

### 13.1 Failure Matrix

| Failure | Impact | Detection | Mitigation |
|---------|--------|-----------|------------|
| **API down** | All requests fail | Health check fails | Auto-restart, route to healthy |
| **DB down** | All writes fail | Connection timeout | Return 503, enable degraded mode |
| **Redis down** | Cache miss, queues pause | Connection timeout | Fallback to DB |
| **Queue stuck** | Async jobs not processing | Queue depth > 10K | Scale workers, alert OPS |
| **Worker crash** | Async jobs fail | Worker exits | BullMQ auto-retry |
| **CDN down** | Static assets slow/fail | CDN health check | Serve from origin |
| **Payment gateway down** | Orders can't be paid | Webhook timeout | Show error, queue for retry |
| **Webhook missed** | Payment status stale | Poll check misses | Cron job polls every 5 min |

### 13.2 Degraded Mode Matrix

| Service Down | Platform Behavior | User Sees |
|--------------|------------------|-----------|
| **Search** | Fallback to basic DB search | "Basic search works" |
| **Redis (cache)** | Read from DB | No visual impact |
| **Redis (session)** | Force re-login | "Please login again" |
| **Notifications** | Queue in DB, process later | No impact |
| **Analytics** | Skip analytics | No impact |
| **Payment gateway** | Show "payment unavailable. Try COD." | "COD available" |
| **Order tracking** | Show last known status | "Contact support" |

### 13.3 Partial Outage Strategy

```
WHEN MULTIPLE SERVICES FAIL:
  1. Activate degraded mode (core features only)
  2. Show global banner: "Some features temporarily unavailable"
  3. Disable non-essential: analytics, notifications, search suggestions, reviews
  4. Keep running: search, products, cart, orders (COD), profile
```

### 13.4 Recovery Runbook

```
1. DETECT: Alert fires (Slack / PagerDuty)
2. TRIAGE: On-call engineer checks dashboard
3. ASSESS: Impact (users affected, data at risk)
4. MITIGATE: Degraded mode, scaling, restart, rollback
5. RESOLVE: Fix root cause
6. VERIFY: Health checks pass, metrics green
7. POSTMORTEM: Document incident, update runbook
```

## 14. SECURITY RUNTIME LAYER

### 14.1 Runtime Security Architecture

```
TRUST BOUNDARIES:
  Public Internet -> Cloudflare (WAF + Rate Limiting)
    -> ALB (TLS termination)
      -> Private Subnet (API + Workers)
        -> PostgreSQL (DB, private subnet)
        -> Redis (private subnet)
        -> S3 (via VPC endpoint)
```

### 14.2 Authentication Runtime

```
JWT VALIDATION:
  - Every API request (except public: /auth/otp/send, /auth/otp/verify)
  - Validation: signature, expiry, audience, issuer
  - Refresh: /auth/refresh endpoint

SESSION MANAGEMENT:
  - Sessions in Redis (TTL: 7 days)
  - Max 3 concurrent sessions per user
  - Old device: Revoke oldest
  - Geo-check: New country = re-verify

RATE LIMITING (Redis):
  - Per IP: 100 req/min
  - Per user: 10 req/sec
  - OTP: 3 per 5 min
  - Logins: 5 per 10 min
  - Blocked: 429 with Retry-After
```

### 14.3 Web Application Firewall (WAF)

| Threat | WAF Rule | Action |
|--------|----------|--------|
| SQL Injection | Pattern match | Block (403) |
| XSS | Script injection | Block (403) |
| Bot traffic | User-agent + behavior | Challenge |
| DDoS | >10K req/sec | Rate limit (429) |
| Credential stuffing | >10 failed logins | Block IP (1 hour) |

### 14.4 TLS & Encryption

```
IN-TRANSIT:
  - TLS 1.3 only
  - HSTS: max-age=31536000
  - Auto-renew certificates

AT-REST:
  - DB: AES-256 (managed)
  - S3: SSE-S3 encryption
  - Backups: Encrypted

SECRETS:
  - Phase 1: env vars (12-factor)
  - Phase 2: Vault / Secrets Manager
```

### 14.5 Runtime Attack Scenarios

|--------|------------|-----------|

| **OTP abuse** | Rate limit | OTP request spike |
| **Queue abuse** | Job size limits | Monitor queue depth |
| **Search abuse** | Rate limit | High search volume |

## 23. RUNTIME MAINTENANCE MODE STRATEGY

### 23.1 Maintenance Types

| Maintenance | Duration | User Impact | Approach |
|-------------|----------|-------------|----------|
| **Hotfix deploy** | < 5 min | Minimal (rolling restart) | Blue-green deploy |
| **Schema migration** | < 15 min | Read-only mode | Forward-compatible, no downtime |
| **Version rollback** | < 5 min | Minimal (traffic switch) | Route to old containers |
| **Scheduled maintenance** | 15-60 min | Read-only, banners | Announce 24h ahead |
| **Emergency maintenance** | Varies | Full shutdown | Show maintenance page |
| **DB maintenance** | 1-4 hours | Read-only mode | Read replica takeover |

### 23.2 Read-Only Mode

```
WHEN ACTIVATED:
  - All POST/PUT/PATCH/DELETE return:
    HTTP 503 + { error: "System in maintenance. Read-only mode active." }
  - GET requests continue (view products, view orders)
  - Cart: View only (no modify)
  - Orders: View only (no place)
  - Payments: Blocked (return 503)
  - Admin: Read-only dashboards

EXPERIENCE:
  - Banner: "VyaparNet is in maintenance. Viewing only."
  - ETA: "Back in ~30 minutes"
  - Contact: support@vyaparnet.com
```

### 23.3 Maintenance Mode Setup

| Component | Behavior |
|-----------|----------|
| **API Gateway** | Return 503 for write operations |
| **Next.js** | Show maintenance banner, disable CTAs |
| **Admin Dashboard** | Read-only (dashboards, analytics) |
| **Database** | Read replica for reads, block writes |
| **Redis** | Continue for cache, block session writes |
| **Queues** | Pause non-critical, allow critical (payments) |
| **Search** | Read-only (no new indexing) |
| **Notifications** | Defer until maintenance end |
| **Webhooks** | Queue for retry after maintenance |
| **Analytics** | Skip (already non-critical) |

### 23.4 Maintenance Decision Matrix

| Decision | Criteria | Action |
|----------|----------|--------|
| **Proceed with maintenance** | < 10% active users, low queue depth, no critical alerts | Activate read-only mode |
| **Postpone maintenance** | > 10% active users, high queue depth, active alerts | Wait + retry later |
| **Emergency maintenance** | Critical security issue, data corruption, payment failure | Immediate activation |
| **Rollback maintenance** | Maintenance causes new errors | Revert to stable version |
