## 1. A/B TESTING / EXPERIMENTATION GOVERNANCE

**Priority**: Post-MVP
**Owner**: Product + Engineering

### Scope

```
A/B TESTING RULES (to be defined in future):
  - No running multiple experiments on the same CTA element
  - Success metrics must be defined BEFORE experiment starts
  - Experiment duration: max 2 weeks (then commit or kill)
  - Minimum sample size: 1000 users per variant
  - Rollout sequence: 5% -> 25% -> 50% -> 100%
  - Feature flag + experiment integration required
  - No experiments on: payment flows, auth flows, security-sensitive areas
  - Statistical significance threshold: 95% confidence
```

### Why Deferred
- Requires analytics infrastructure (Mixpanel/Amplitude) not in MVP
- Requires experiment platform (GrowthBook or LaunchDarkly)
- B2B user base needs sufficient volume for valid experiments

## 2. INTERNATIONALIZATION (i18n) EDGE CASES

**Priority**: Post-MVP Phase 2+
**Owner**: Frontend + Content

### Scope

```
TRANSLATION EXPANSION RULES:
  - Hinglish (Roman) is MVP only
  - Phase 2: Devanagari Hindi, Tamil, Telugu, Marathi, Bengali, Gujarati
  - Text expansion: Budget 30% extra width for translations
    (e.g., "Submit" in English vs "जमा करें" in Hindi may be 50% wider)

RTL FUTURE SUPPORT:
  - No explicit RTL layout in v1
  - CSS must NOT assume left-to-right (use logical properties)
  - body { direction: ltr } by default; no hardcoded left/right values

FONT FALLBACK STRATEGY:
  - Primary: Inter
  - Fallback: Noto Sans, system-ui
  - Indian scripts: Noto Sans Devanagari, Noto Sans Tamil, etc.
  - All fonts loaded from Google Fonts with unicode-range subsetting

LONG-TEXT OVERFLOW:
  - Cards must handle text 3x expected length without breaking
  - Test with: "अत्यंत लंबा पाठ यहाँ हो सकता है जो सीमा से अधिक है"
  - Buttons: max 5 words visible (ellipsis + tooltip for rest)
```

### Why Deferred
- MVP is Hindi-English only (Hinglish in Roman script)
- Language team and native review not yet engaged
- Font subsetting requires language-specific build

## 3. DESIGN ANALYTICS & UX METRICS PLATFORM

**Priority**: Post-MVP Phase 2+
**Owner**: Product + Data

### Scope

```
UX METRICS TO INSTRUMENT:

Task Completion Time:
  - Time from search to order placed (target: <5 min)
  - Time from cart open to checkout (target: <2 min)
  - Measured per user segment (new vs. repeat buyers)

Rage Click Detection:
  - Already defined in UX System (Section 60.1)
  - Implementation: 3 clicks within 500ms on same element

Drop-off Rate Per Funnel Step:
  - Home → Search → PDP → Cart → Checkout → Payment → Confirm
  - Segment by: device, user type (buyer/seller), segment (textile/spare)

Search Abandonment:
  - Query logged when user types but submits no search
  - "No results" rate tracked separately

Failed Retry Rate:
  - Track: how many users retry after failure
  - Track: how many give up after 2+ retries

Session Replay (Future):
  - Hotjar / FullStory for qualitative analysis
  - Privacy: anonymized, no PII captured
  - Sample: 5% of sessions
```

### Why Deferred
- MVP uses basic analytics (Pageviews + events via PostHog)
- Session replay requires privacy legal review (GDPR)
- Requires data team to define dashboards

## 4. COMPONENT DOCUMENTATION STRATEGY (Storybook)

**Priority**: Post-MVP Phase 2
**Owner**: Frontend

### Scope

```
STORYBOOK STRUCTURE (to be defined later):

Each component story includes:
  - Meta: component name, version, owner, status
  - Props table: name, type, default, required, description
  - Variants: all visual variants (default, hover, active, disabled, loading, error, etc.)
  - Accessibility: ARIA notes, keyboard behavior, screen reader behavior
  - Usage: When to use, when NOT to use
  - Do/Don't: Visual examples of correct and incorrect usage
  - Related: Links to related components

EXAMPLE (Button story):
  Status: stable | deprecated | experimental

  Variants:
    [ ] Primary (default, hover, active, disabled, loading)
    [ ] Secondary
    [ ] Ghost
    [ ] Danger

  Accessibility:
    - role="button" (native <button> tag preferred)
    - Disabled: aria-disabled="true" (NOT disabled attribute for tooltips)
    - Loading: aria-busy="true", aria-label="Submitting..."

  Do:
    - Use for primary actions (1 per screen)
    - 48px min-height for touch targets
    - Icon + label combinations (icon must have aria-label if standalone)

  Don't:
    - Multiple primary buttons on same screen
    - Truncated text on buttons
    - Icon-only buttons without aria-label
```

### Why Deferred
- Storybook setup is implementation phase work
- Component library must stabilize first before documenting
- This is a frontend team deliverable, not architecture work

## 5. PROCUREMENT WORKFLOW DEEP DIVE

**Priority**: Post-MVP Phase 2-3
**Owner**: Product + Engineering

### Scope

```
ENTERPRISE PROCUREMENT (beyond basic RFQ in UX System Section 53):

APPROVAL CHAINS:
  - Rule: Order >₹50,000 requires manager approval
  - Approval flow: Buyer submits → Manager reviews → Finance approves → Order confirmed
  - SLA: 24h for approval, auto-escalation after timeout

BUDGET LIMITS:
  - Per-buyer monthly credit limit
  - Per-category spend caps
  - Cross-budget alerts (soft: warning; hard: block)

PURCHASE ORDER (PO) GENERATION:
  - System-generated PO numbers
  - PDF export with GST details, HSN codes
  - PO matching: PO vs. Goods Received Note (GRN) reconciliation

VENDOR COMPARISON:
  - Side-by-side comparison of up to 5 sellers
  - Comparison dimensions: price, delivery, rating, MOQ, payment terms
  - Shortlist + rank feature

REPEAT ORDER AUTOMATION:
  - Scheduled orders (weekly/monthly/quarterly)
  - Auto-reorder when stock below threshold
  - Approval required before auto-order executes

SUPPLIER SCORECARD:
  - On-time delivery rate
  - Quality score (QC pass rate)
  - Price competitiveness
  - Communication responsiveness
```

### Why Deferred
- MVP ships basic RFQ (1 RFQ → multiple quotes → select winner)
- Approval chains and PO generation require ERP integration planning
- Budget limits require finance module which is Phase 2

## 6. DESIGN OPERATIONS & SCALE TOOLS

**Priority**: Post-MVP Phase 2
**Owner**: Design + Frontend

### Scope

```
DESIGN SYSTEM MAINTENANCE TOOLS:

Figma ↔ Code Sync:
  - Tokens Studio (Figma plugin) for design token sync
  - CI job: detect token changes → auto-create PR in packages/tokens
  - Version bump: automated based on DDR change classification

Visual Regression Testing:
  - Chromatic (storybook visual regression)
  - Playwright screenshot tests for critical flows
  - CI gate: any visual regression blocks merge

Design Token Pipeline:
  Figma tokens → JSON → packages/tokens → CSS variables + JS export
  Tool: Style Dictionary (Amazon)
  Frequency: On-demand (token changes are rare, manual trigger OK)

Accessibility Linter (CI):
  - axe-core in pre-commit hook
  - eslint-plugin-jsx-a11y for JSX
  - Lighthouse CI in GitHub Actions

Component Usage Analytics:
  - Track which components are used most/least
  - Identify: overused components (possible God Component)
  - Identify: deprecated components still in codebase
  - Tool: design-tokens-report or custom script

DESIGN REVIEW CADENCE:
  - Weekly design review meeting (30 min)
  - Review: new DDRs, component status changes, deprecations
  - Owners must attend for their components
```

### Why Deferred
- MVP phase: manual processes are fine
- Tooling added when team grows past 3 frontend engineers
- Design ops maturity needed before automating
