## PART 1: FOUNDATION

### 1. UX PHILOSOPHY & PRINCIPLES

#### Core Philosophy
```
SPEED > BEAUTY
SEARCH-FIRST
LOW COGNITIVE LOAD
BUYER-FIRST THINKING
REPEAT BUYING OPTIMIZED
MOBILE-FIRST (Low-end Android)
```

#### 1.1 Bharat-First UX Thinking
| Principle | Rule |
|-----------|------|
| **Speed over beauty** | No fancy animations. Subtle micro-interactions only. |
| **Low friction** | Minimal clicks to complete tasks. |
| **Low literacy support** | Icons + Hindi text. Minimal English. |
| **Large touch targets** | Minimum 44x44px for all interactive elements. |
| **Predictable navigation** | Same pattern across all screens. |
| **Minimal typing** | Voice search placeholder, quick selects, recent picks. |
| **Visual filters** | Filter by image, not just text. |
| **Trust signals** | GST verified badge, ratings, delivery promises. |

#### 1.2 Performance-First Rules
```
TARGET DEVICES: Low-end Android (2GB RAM, slow 3G)
PAGE LOAD: < 2 seconds
INTERACTION: < 100ms feedback
SEARCH: < 150ms suggestions
LIST RENDER: Virtual scrolling (100+ items)
IMAGES: WebP, lazy loading, blur placeholder
```

#### 1.3 Search-First Commerce
```
HOMEPAGE = SEARCH BAR (not banner)
70% of user journeys start with search
Search suggestions visible on homepage
Recent searches persistent
Trending searches visible
Category shortcuts below search
```

#### 1.4 Repeat Buying Optimization (B2B Critical)
```
HOMEPAGE SECTIONS:
1. Recent Orders (1-tap reorder)
2. Saved Procurement Lists
3. Frequently Bought Items
4. Subscription Orders
5. Reorder Reminders (low stock alert)
```

### 2. DESIGN LANGUAGE SYSTEM

#### 2.1 Color Palette (NO DARK MODE)

| Role | Hex | Usage |
|------|-----|-------|
| **Primary** | `#2563EB` | Buttons, links, active states |
| **Primary Dark** | `#1D4ED8` | Hover states |
| **Secondary** | `#0D9488` | Success indicators, secondary actions |
| **Accent** | `#F59E0B` | CTAs, highlights, urgency |
| **Success** | `#10B981` | Order placed, payment success |
| **Warning** | `#F59E0B` | Low stock, pending actions |
| **Error** | `#EF4444` | Failed payment, validation errors |
| **Background** | `#F8FAFC` | Page background |
| **Surface** | `#FFFFFF` | Cards, modals, sheets |
| **Border** | `#E2E8F0` | Subtle borders, dividers |
| **Text Primary** | `#1E293B` | Headings, body text |
| **Text Secondary** | `#64748B` | Captions, labels |
| **Text Disabled** | `#94A3B8` | Disabled states |

#### 2.2 Typography
```
FONT FAMILY: Inter (primary), Manrope (headings)
SCALE:
  Display: 32px / bold / -0.02em (hero headings)
  H1: 24px / bold (page titles)
  H2: 20px / semibold (section headers)
  H3: 16px / semibold (card titles)
  Body: 14px / regular (primary text)
  Caption: 12px / regular (labels, metadata)
  Micro: 10px / medium (badges, timestamps)

LINE HEIGHT: 1.5 (body), 1.25 (headings)
```

#### 2.3 NO DARK MODE
```
RATIONALE:
- B2B users: daytime usage
- Low-end screens: poor dark mode rendering
- Simpler codebase = faster execution
- Consistency across all user types
```

### 5.6 UNIVERSAL COMPONENT STATES MATRIX

Every UI component MUST implement these states consistently.

#### State Definition Table

| State | Visual Behavior | Interaction | Accessibility |
|-------|----------------|-------------|---------------|
| **default** | Base design (no modifications) | Normal cursor | Role + label announced |
| **hover** | Elevation + subtle border-color shift, 150ms | Pointer cursor | Focus visible |
| **active / pressed** | scale(0.98), darker background, 100ms | Default cursor | Active state announced |
| **focus** | 2px outline (primary color), 2px offset | Keyboard-only | Focus announced to screen reader |
| **loading** | Spinner replaces content OR overlay, pointer-events: none | Disabled | "Loading" state + label announced |
| **disabled** | Opacity 50%, cursor: not-allowed, pointer-events: none | None | aria-disabled="true", role announced |
| **success** | Green border OR green icon, checkmark | Read-only | Status announced |
| **warning** | Yellow border OR yellow icon, triangle | Read-only | Warning announced |
| **error** | Red border OR red icon, X mark | Read-only | Error announced |
| **skeleton** | Pulse animation (#E2E8F0 shimmer), matches final layout | None | aria-busy="true" |
| **offline** | Muted overlay OR banner, all interactions blocked | Disabled | "Offline" announced |
| **selected** | Primary color background tint, checkmark (if applicable) | Selectable | Selected state announced |
| **expanded** | Content revealed, chevron rotated | Expandable | Expanded/collapsed announced |
| **empty** | Illustration + contextual message + primary action | CTA clickable | Empty state announced |

#### State Implementation Rules

```
1. Each component MUST implement ALL states above
2. State transitions: max 150ms for micro, 300ms for layout changes
3. Loading state never blocks the entire page (use skeleton for content areas)
4. Disabled state: opacity 50%, cursor not-allowed, aria-disabled=true
5. Error state: always show inline message (never tooltip-only)
6. Skeleton MUST match final layout dimensions exactly (no CLS)
7. Never show only color to communicate state (always pair with icon/text)
```

#### Component State Priority

```
CRITICAL (must always work):
  default, hover, active, focus, disabled, error

HIGH (should work):
  loading, success, warning, skeleton

MEDIUM (nice to have):
  offline, selected, expanded, empty
```

#### 29.2 Token Versioning Policy

```
BREAKING TOKEN CHANGE (major version bump, e.g., v2.0.0):
  - Renaming any token name
  - Changing token value by more than 10%
  - Removing a token

ADDITIVE CHANGE (minor version bump, e.g., v1.5.0):
  - Adding new tokens
  - Adding new token scales (e.g., spacing-3xl)

DEPRECATION CYCLE:
  - Mark token as deprecated (with replacement) for 1 release cycle
  - Log console warning when deprecated token is used
  - Remove in next major version

MIGRATION:
  - Token rename: codemod script provided
  - Value change: manual review required
  - Breaking changes: migration guide in release notes
```

#### 29.3 Accessibility Deep Dive Patterns

```
SCREEN READER ANNOUNCEMENTS:
  - Page load: "Page loaded. [Title]."
  - Modal open: "[Modal title] dialog. [n] items."
  - Toast: "[Type]: [Message]. [Action]."
  - Error: "[Field] error. [Message]."
  - Loading: "Loading [content type]."
  - Success: "[Action] successful."

KEYBOARD TRAP PREVENTION:
  - Tab should never get stuck in an element
  - Modals: Escape closes, Tab cycles within
  - Dropdowns: Escape closes, arrow keys navigate
  - Never trap keyboard in: tooltips, dropdowns, modals permanently

REDUCED MOTION:
  - Respect prefers-reduced-motion
  - Replace all transitions with instant states
  - No pulse/shimmer animations
  - No auto-playing animations
  - Exceptions: spinner only (1 rotation loop), essential feedback only

FOCUS MANAGEMENT:
  - Focus moves to: new modals, toasts, error fields
  - Focus returns to: trigger element when modal closes
  - Skip links: "Skip to main content" as first focusable element
  - Focus visible: 2px outline, primary color, 2px offset (never removed)
```

#### 29.4 Chart System Governance

```
CHART RULES:
  - Max 5 distinct colors per chart
  - No pie charts with >5 segments (use bar chart instead)
  - Tooltip required on all data points
  - Accessible: color is never the only differentiator (pair with pattern or label)
  - Legend required (positioned below chart on mobile)
  - Axis labels always visible

MOBILE ADAPTATION:
  - Charts collapse to single-series on mobile (<768px)
  - Horizontal bar charts preferred over vertical on mobile
  - Data tables shown as alternative to charts on mobile
  - Touch targets: 44px minimum on chart controls

CHART ANIMATION:
  - Max 300ms
  - ease-out only
  - No animation on initial load (shows data immediately, animates in)
```


#### 45.3 Enterprise Form Architecture Rules

All forms follow these strict governance rules:

##### Optimistic Submit Pattern

```
FLOW:
  1. User submits form
  2. IMMEDIATELY show success state (do not wait for server)
  3. Send request to server (background)
  4. If server fails: Rollback UI, show error, restore form data

ROLLBACK BEHAVIOR:
  - Re-populate all fields with submitted values
  - Show error toast: "Submission failed. Your data is restored."
  - Highlight fields that need correction
  - Do NOT clear the form (user should not re-type)
```

##### Duplicate Submit Prevention

```
RULE: Disable submit button immediately on click
VISUAL: Button shows spinner, text changes to "Submitting..."
TIMEOUT: Re-enable after 30s if no response (show error)
RETRY: User must explicitly click "Retry" after failure
```

##### Dirty Form Detection

```
TRIGGER: Any field value changes from initial state
ON NAVIGATE AWAY:
  - Show warning modal: "You have unsaved changes"
  - Buttons: "Save Draft" / "Discard" / "Cancel"
  - Do NOT auto-save without user consent
```

##### Async Validation Governance

```
DEBOUNCE: 500ms after user stops typing
VISUAL: Show spinner inside field while validating
CACHE: Cache validation results (key = field value, TTL = 5 min)
ERROR: Show below field (not tooltip, not toast)
SUCCESS: Optional green checkmark
ABORT: Cancel previous validation request when new one starts
```

##### Field Dependency Rules

```
DEPENDENT FIELDS:
  - Child field disabled until parent is valid
  - Example: City dropdown disabled until State selected
  - Example: PIN code auto-fills after Address saved

DEPENDENCY GRAPH:
  - Country -> State -> City -> PIN -> Address
  - Clear dependent fields when parent changes (with warning)
```

##### Form Submission Retry Queue

```
FAILED SUBMISSION:
  1. Store in retry queue (IndexedDB)
  2. Show persistent banner: "Submission pending. Retrying..."
  3. Auto-retry: 5s, 15s, 30s, 2min, 5min (exponential backoff)
  4. After max retries: "Could not submit. Save as draft and try later."
  5. On app reopen: Resume retry queue if network available
```

##### Multi-Step Form Navigation

```
PROGRESS INDICATOR:
  - Stepper (top), mobile-friendly
  - Completed steps: Green checkmark
  - Current step: Bold, Primary color
  - Remaining steps: Gray

STEP VALIDATION:
  - Validate before next step (block navigation if invalid)
  - Show summary at final step
  - Allow back navigation WITHOUT re-validating previous steps

SAVE PROGRESS:
  - Auto-save between steps (localStorage)
  - Resume from last completed step on revisit
```

##### Mobile Input Optimization
```
PROGRESS INDICATOR:
  - Stepper (top), mobile-friendly
  - Completed steps: Green checkmark
  - Current step: Bold, Primary color
  - Remaining steps: Gray
```

#### 60.5 Experiment & A/B Testing Governance

Full experimentation platform is Phase 2. This defines governance only.

```
EXPERIMENT NAMING:
  Format: [feature]-[hypothesis]-[date]
  Example: checkout-step-reduction-v1-20250601

  - Primary metric: e.g., checkout completion rate (+5%)
  - Secondary metric: no regression in support ticket rate
  - Guard metric: no increase in rage clicks

ROLLBACK RULES:
  - Auto-stop: primary metric drops >10% in first 100 sessions
```

### 61. DESIGN DECISION RECORDS (DDR)

> **Purpose:** Every major UX/architecture decision must be documented so future teams understand the "why" behind choices. Prevents decision rot after team turnover.

#### 61.1 When to Write a DDR

```
REQUIRED for:
  - New component patterns (e.g., how to build a data table from scratch)
  - UX flow changes (e.g., changing checkout from 4 steps to 2 steps)
  - Design token changes (e.g., renaming or redefining a semantic token)
  - Interaction changes (e.g., swipe-to-delete vs. tap-to-select)
  - Responsive behavior changes (e.g., collapsing tables to cards at 768px)
  - Accessibility exceptions (e.g., why a pattern cannot meet WCAG 2.1 AA)

NOT REQUIRED for:
  - Bug fixes (use PR description instead)
  - Minor UI tweaks (copy, color shade, spacing adjustments)
  - Documentation updates
  - Routine frontend work
```

#### 61.2 DDR Template

```
# DDR-[number]: [Short Title]

Date: YYYY-MM-DD
Author: [Name + Role]
Status: PROPOSED | ACCEPTED | REJECTED | DEPRECATED

## Problem Statement
[What user/business problem are we solving?]

## Options Considered
1. [Option name]
   - Pros:
   - Cons:
2. [Option name]
   - Pros:
   - Cons:

## Decision
[What was chosen and why?]

## Consequences
[What changes in the system after this decision?]

## Trade-offs Acknowledged
- Less "all-in-one" visibility (acceptable; summary shown before payment)
```

#### 61.5 DDR Lifecycle & Process

```
LIFECYCLE:
  PROPOSED → REVIEW → ACCEPTED → (DEPRECATED)

PROPOSED:
  - Author writes DDR using template (61.2)
  - Assigns reviewers (minimum: 1 senior eng + 1 PM/designer)
  - Labels PR with: design-decision

REVIEW:
  - Reviewers have 5 business days to respond
  - Discussion in PR comments (not Slack)
  - Consensus goal; if split, PM makes final call

ACCEPTED:
  - Merge to /docs/ddr/
  - Tag: @frontend-team / @design-team
  - Update index README with status + date

DEPRECATED:
  - Update DDR status to DEPRECATED
  - Add "Superseded by: DDR-[n]" in body
  - Keep old DDR (never delete, historical record)

DDR INDEX (README.md):
  ## Accepted | ## Under Review | ## Deprecated

DECISION DEBT LIMIT:
  Max 5 open PROPOSED DDRs at any time
```

#### 61.3 DDR Repository

```
Location: /docs/ddr/ (Markdown files)
Naming: DDR-001-[short-title].md
Index: /docs/ddr/README.md (list of all DDRs by status + date)

Review: Any DDR affecting UX requires sign-off from:
  - Senior frontend engineer
  - Product designer or product manager
```

#### 61.4 Example DDR

```
# DDR-007: Two-tap checkout vs. single-page checkout

Date: 2025-05-22
Author: [PM]
Status: ACCEPTED

## Problem: Checkout drop-off at step 2 (payment) is 40%

## Options Considered
1. Single-page checkout: Load all steps at once
   - Pros: User sees full picture; no navigation
   - Cons: Heavy page load; complex mobile form

2. Two-tap checkout (current): Address tap → Payment tap
   - Pros: Lightweight; familiar pattern; low cognitive load
   - Cons: More navigation

## Decision
Two-tap checkout chosen. Mobile-first context favors lightweight pages.

## Consequences
- PDP → Checkout: 2 steps (address, payment + review)
- Server-side validation at each step
- Cart persisted in Redis

## Trade-offs
- Less "all-in-one" visibility (acceptable; summary shown before payment)
```
