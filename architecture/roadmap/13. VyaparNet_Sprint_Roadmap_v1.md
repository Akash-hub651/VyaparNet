## 1. ROADMAP PHILOSOPHY

### 1.1 Core Execution Principles

```
SHIP SMALL INCREMENTS
  - Sprint duration: 2 weeks
  - Goal: working system every sprint (not just code)
  - Demo at end of every sprint (to stakeholders)
  - Deploy to staging after every sprint merge

CORE FLOWS FIRST
  - Path to revenue: buyer -> search -> product -> cart -> order -> payment
  - Everything else is secondary until this works end-to-end
  - Admin flows (approval, moderation) only after buyer flow works

STABILITY BEFORE FEATURES
  - Phase 1 (Sprint 0-3): Infra, auth, core CRUD (stable foundation)
  - Phase 2 (Sprint 4-6): Commerce flows (critical path)
  - Phase 3 (Sprint 7-9): Operational maturity (admin, observability, hardening)

DB INTEGRITY FIRST
  - Schema correctness and data integrity over speed
  - Every sprint: backward-compatible migrations only
  - No schema changes without migration + rollback plan

ASYNC WHERE POSSIBLE
  - Heavy processing in queues (notifications, analytics, search reindex)
  - Sync path: auth, CRUD, order placement
  - Async path: search reindex, email, analytics, image processing

UX POLISH AFTER RELIABILITY
  - First: Core flow works
  - Then: UX polish (loading states, empty states, transitions)
  - Never ship with broken core flow for "nicer UI"

PROTECT CHECKOUT PATH
  - Checkout path is sacred: search -> product -> cart -> order -> payment -> confirmation
  - Any change affecting checkout path requires extra review
  - Checkout flow regression = ship-blocker (not "nice to have")

AVOID PREMATURE COMPLEXITY
  - No microservices in MVP (monolith only)
  - No Kafka in MVP (BullMQ sufficient)
  - No multi-region in MVP (single region: India only)
  - No real-time WebSocket in MVP (polling acceptable)
  - No advanced AI/ML in MVP (rule-based first)

MEASURE BEFORE OPTIMIZING
  - Don't optimize code without performance data
  - Don't add caching without evidence of need
  - Don't add read replicas without DB CPU > 60%
  - Profile first, optimize second
```

### 1.2 Execution Anti-Patterns

```
❌ WRONG: Plan 100 features at once
✅ RIGHT: Plan sprint-by-sprint, adapt after each sprint

❌ WRONG: Backend starts after frontend mockups
✅ RIGHT: Backend and frontend work in parallel (API contracts first)

❌ WRONG: Full system built, then tested
✅ RIGHT: Tested incrementally every sprint

❌ WRONG: Ship with known checkout bugs to add "one more feature"
✅ RIGHT: Fix checkout first, then add features

❌ WRONG: Optimize for 100K users before first paying customer
✅ RIGHT: Optimize when actual metrics justify it (measure first)

❌ WRONG: Perfect CI/CD on day one
✅ RIGHT: Basic CI/CD on day one, mature CI/CD by Sprint 3

❌ WRONG: All teams work in isolation
✅ RIGHT: Daily sync, API contract review, cross-sprint dependencies tracked
```

## 4. SPRINT EXECUTION MODEL

### 4.1 Sprint Cadence

```
SPRINT DURATION: 2 weeks (10 working days)
TEAM SIZE: 6-8 engineers (3-4 full-stack, 2-3 backend, 1-2 frontend, 1-2 QA/DevOps)

SPRINT STRUCTURE:
  Day 1: Planning (half day)
  Day 2-9: Development
  Day 10: Demo + Retrospective + Planning prep
```

### 4.2 Definition of Ready (DoR)

A feature/ticket is ready only whenALL of the following are true:

```
✅ User story clear (As a [user], I want [action] so that [outcome])
✅ Acceptance criteria defined (3-5 clear conditions)
✅ API contract defined (if backend changes)
✅ UX mockup or wireframe approved (if UI changes, not final design)
✅ Database schema defined (if DB changes)
✅ Dependencies identified and unblocked (if any)
✅ Effort estimated (story points: 1,2,3,5,8,13)
✅ No blockers: backend API ready, mock data available, design approved
```

### 4.3 Definition of Done (DoD)

A feature is done only when ALL of the following are true:

```
✅ Code written, reviewed, and merged to develop
✅ Tests: unit, integration (e2e for critical flows)
✅ Code coverage >= 70% (for new code)
✅ Manual testing passed (on local + staging)
✅ RBAC checked (if applicable)
✅ Audit logs emitted
✅ Error handling implemented (no uncaught errors)
✅ Loading states handled (skeleton or spinner)
✅ Error states handled (user-friendly error messages)
✅ Metrics/logs added (for observability)
✅ API documentation updated (if applicable)
✅ Performance acceptable (no obvious regressions: < 100ms local, < 300ms staging)
✅ Accessibility checked (keyboard nav, screen reader labels)
✅ Regression tests passed (critical flows still work)
```

### 4.4 Story Points & Velocity

| Points | Meaning | Example |
|--------|---------|---------|
| **1** | Trivial (typo, copy change) | Button label update |
| **2** | Simple (single component) | Add toast notification |
| **3** | Standard (single API+UI feature) | Add filter dropdown |
| **5** | Complex (multi-component, integration) | Order tracking page |
| **8** | Very complex (new module, 2+ integrations) | Checkout flow redesign |
| **13** | Epic-level (needs breakdown) | Full B2B procurement |

```
TEAM VELOCITY (estimated):
  Sprint 1: 20 points (forming, slower)
  Sprint 3+: 35 points (stable team)
  Sprint capacity: 35-40 points per sprint

BUDGET RULE:
  Never plan more than 85% of sprint capacity per sprint.
  Reserve 15% for: bugs, production issues, unplanned tasks.
```

## 6. PARALLEL WORK STRATEGY

### 6.1 Frontend/Backend Decoupling

| Team | Sprint Dependency | Can Start Before Backend? |
|------|-------------------|--------------------------|
| **Frontend** | Sprint 1-2 | Yes via mock API (Swagger/OpenAPI) |
| **Backend API** | Sprint 1-2 | No (needs API contract first) |
| **Admin** | Sprint 3-7 | Partial (some screens, limited actions) |
| **QA** | Sprint 2+ | No (waits for feature branch) |
| **DevOps** | Sprint 0 | Independent (infra first) |
| **Product** | Sprint 0-6 | Independent (research, requirement) |
| **Design** | Sprint 1-3 | Independent (mockups, component library) |

### 6.2 Mock API Governance (Contract-First)

```
CONTRACT-FIRST DEVELOPMENT:
  1. Backend defines OpenAPI spec (Swagger) BEFORE coding
  2. Frontend uses mock server based on OpenAPI (mockaroo, prism)
  3. Frontend develops UI using mock data
  4. Backend implements API to match contract
  5. Integration happens when both are ready (sprint end)

MOCK API RULES:
  - Backend commits OpenAPI spec to repo BEFORE sprint start
  - Frontend uses mock server for all development (no waiting for backend)
  - Mock data: realistic, edge cases included (empty lists, errors)
  - Contract updated ONLY by mutual agreement (breaking changes blocked)
  - Integration tests: verify frontend + backend contract match
```

### 6.3 API Contract Review Cadence

```
DAILY (15 min):
  - Frontend + Backend sync on API changes
  - Review: endpoint changes, DTO changes, breaking changes

WEEKLY:
  - Full API contract review (swagger diff)
  - Resolve conflicts, update mocks
  - Both teams agree on next sprint's API additions
```

## 7. ENGINEERING GOVERNANCE

### 7.1 Code Standards

```
STRICT TYPESCRIPT:
  - no "any" anywhere (use "unknown" + validate)
  - DTOs must be validated (Zod / class-validator / DTO decorator)
  - All async errors caught (try/catch, .catch())
  - No console.log in production (use logger interface)
  - No magic numbers (use named constants)

FORMATTING:
  - Prettier (enforced in CI)
  - ESLint (error on warnings)
  - Import sorting (enforced)

TYPING:
  - All API responses typed (DTO)
  - All DB queries typed (Prisma generated types)
  - Shared types in packages/types (no duplication)
```

### 13.2 Security Dos and Don'ts

```
✅ DO:
  - Sanitize all user input (XSS, SQL injection)
  - Rate limit: per IP, per user
  - Validate file uploads (type, size, dimensions)
  - Store secrets in env vars (never in code)
  - Hash passwords (bcrypt, Argon2)
  - Encrypt PII at rest (AES-256)
  - Sign webhooks (HMAC verification)
  - Log security events (brute force, suspicious login)

❌ DON'T:
  - Expose DB to public internet
  - Log passwords, OTP, or tokens
  - Trust client-side validation (always validate server-side)
  - Allow unlimited file sizes or types
  - Skip rate limiting on auth endpoints
  - Ignore security alerts (CVEs, dependency issues)
```
