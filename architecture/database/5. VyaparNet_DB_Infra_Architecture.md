# VyaparNet - Database & Infrastructure Architecture (Enterprise v2.0)

## 1. REQUIRED PRE-DB DOCUMENTS

### 1.1 Data Classification Matrix

Every piece of data in the system must be classified at creation. This dictates its storage, backup, retention, and access policies.

| **Data Class** | **Example** | **Storage** | **Backup** | **Retention** | **Access Level** |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Critical Transactional** | Orders, Payments, Invoices | Primary DB + WAL | Real-time (RPO < 5 min) | Permanent (7 years) | Restricted |
| **Immutable** | Audit Logs, Event History | Primary DB (Partitioned) | Daily Snapshots | 1-2 years | Read-Only |
| **Temporary / Ephemeral** | OTPs, Whatsapp Codes, Session Tokens | In-Memory (Redis) or Ephemeral Columns | None | < 15 minutes | Internal Only |
| **Cacheable** | Trending Products, Search Suggestions, Aggregated Stats | Redis / ElastiCache | None | Based on TTL (5-60 min) | Public |
| **Archival** | Old Notifications, Delivered Order History | S3 Glacier / Parquet files | Monthly Snapshots | 30-90 days then Archive | Read-Only / Admin |
| **PII / Sensitive** | GST Numbers, PAN, KYC Docs, Phone Numbers | Encrypted RDS Columns, Encrypted S3 | Encrypted Snapshots | Permanent (GDPR/ compliance) | Strict RBAC |
| **Media** | Product Images, KYC PDFs | S3 Standard + Infrequent Access | Versioned | Lifecycled to IA after 90 days | Public (Images) / Restricted (KYC) |

### 1.2 State Machine Definitions

To ensure data integrity and prevent impossible states, all major domain entities must follow strict state machines.

**Order State Machine:**
```
DRAFT --> PLACED --> CONFIRMED --> SHIPPED --> DELIVERED --> COMPLETED
PLACED --> CANCELLED
CONFIRMED --> CANCELLED
SHIPPED --> CANCELLED
DELIVERED --> RETURN_INITIATED --> RETURN_APPROVED --> RETURNED --> REFUNDED
```

**Payment State Machine:**
```
PENDING --> PAID
PENDING --> FAILED
PENDING --> TIMEDOUT
PAID --> REFUND_INITIATED --> REFUNDED / REFUND_FAILED
```

### 1.3 Search Architecture Spec

PostgreSQL tsvector + GIN indexes handle the Bharat-scale MVP.
Post-MVP, the application is wired to swap in OpenSearch or Typesense via a repository pattern.

**MVP Search Capabilities:**
- **Exact Match:** Product name, SKU, seller name.
- **Prefix Match:** "crom" -> "Crompton Greaves".
- **Synonym Expansion:** "kurtee", "kurta set" mapped to "kurti".
- **Typo Tolerance (Levenshtein Distance):** fuzzystrmatch extension for up to 2 character edits.
- **Segment Isolation:** Search results are strictly filtered by segmentId.

**Search Indexing Strategy:**
- **Primary Searchable Fields:** Product.name, Product.description, Category.name, SubCategory.name.
- **Ranking Strategy:** ts_rank with weights (Name: 1.0, Description: 0.4).
- **Hindi/English Handling:** Unified search_vector column populated with both English and common Hinglish translations.
- **Transliteration:** Pre-computed mapping table for common terms.

## 2. MULTI-TENANCY & ISOLATION STRATEGY

### 2.1 Current Strategy (MVP): Single DB + Strict Segment Isolation

**Decision:** Use a single PostgreSQL database with segmentId as a required column on every table that is segment-specific.

**Rules:**
- segmentId is a mandatory indexed column on all core tables (Product, Category, Inventory, Order, etc.).
- All queries MUST filter by segmentId.
- Prisma middleware enforces @default(segmentId) or throws application-level ForbiddenError if the user's segment doesn't match the record's segment.
- There is NO cross-segment data access for non-admins.

### 2.2 Future Strategy (Post-MVP): Horizontal Sharding

**Plan:**
- When a single segment (e.g., Spare Parts) generates > 1M orders/month, it will be moved to its own schema (Schema-per-segment).
- The application will support switching the Prisma client to a different connection string dynamically.
- The segmentId column will remain to maintain historical data consistency during migration.

### 3.3 Database Partitioning Strategy

**Tables to be partitioned:**
- Order: Partitioned by orderMonth (Range Partitioning).
- AuditLog: Partitioned by createdAt (Monthly).
- Notification: Partitioned by createdAt (Monthly).
- EventStore (Outbox Table): Partitioned by createdAt (Monthly).

**Why Range Partitioning?**
- Orders grow infinitely. Queries are 90% time-bounded (e.g., "Orders from last month").
- Archiving old data becomes a simple DETACH PARTITION + DROP.
- Improves query performance on time-series data.

**Implementation:**
```sql
-- Example for Order table
CREATE TABLE orders_2025_05 PARTITION OF "Order"
FOR VALUES FROM ('2025-05-01') TO ('2025-06-01');
```

### 3.4 Read/Write Split Architecture

**Architecture Pattern:**
- **Primary DB (Writer):** Handles all INSERT, UPDATE, DELETE operations.
- **Read Replica(s):** Handles all SELECT queries.
- **Prisma:** Use readReplicas extension to route read queries to the replica.

**Prisma Configuration:**
```typescript
import { readReplicas } from '@prisma/extension-read-replicas'
const prisma = new PrismaClient().$extends(
  readReplicas({
    url: process.env.DATABASE_REPLICA_URL,
  }),
)
```

**Cache Layer:**
- **Redis:** Caches frequently accessed read data (e.g., Product Details, User Profile) with a TTL of 5-15 minutes.
- **Architecture-Ready:** The application must be able to fall back to the Primary DB if the Read Replica is down.

### 3.5 Concurrency & Inventory Consistency

**The Problem:** Two buyers try to purchase the last 50 kg of cotton simultaneously.

**Solution: Pessimistic Locking with Inventory Reservation**
1. When an order is placed, a row-level lock is acquired on the Inventory record.
2. The reservedQty is incremented.
3. An InventoryReservation record is created with an expiration time (e.g., 15 minutes).
4. If the order is not confirmed (payment fails), a background job releases the reservation (decrements reservedQty).

**Inventory Model Update:**
model InventoryReservation {
  id          String    @id @default(cuid())
  inventoryId String
  orderId     String
  quantity    Int
  status      ReservationStatus @default(ACTIVE)
  expiresAt   DateTime
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt
}

enum ReservationStatus { ACTIVE, CONSUMED, EXPIRED, CANCELLED }

**Optimistic Locking:**
- The version column in Inventory and Order tables prevents "last write wins" scenarios. Prisma is configured to check the version before updating.

### 3.6 Event Versioning

All events published to the Outbox table must include a version.

**Event Envelope:**
```json
{
  "eventId": "uuid-v4",
  "eventType": "OrderPlaced",
  "eventVersion": "1.0",
  "schemaVersion": "2.4.1",
  "timestamp": "2025-05-22T10:00:00Z",
  "payload": { "orderId": "ord-123", "totalAmount": 45000 }
}
```

**Why?**
- Allows consumers to handle different event versions gracefully.
- Prevents breaking changes in downstream microservices (or modules) when the event schema changes.

### 3.7 Connection Pooling (PgBouncer)

**Why?**
- Node.js applications are single-threaded but can open many connections. PostgreSQL has a limit on active connections.
- PgBouncer (Transaction Pooling) is required to prevent connection exhaustion.

**Configuration:**
- **Pool Mode:** Transaction (recommended for Prisma).
- **Max Client Conn:** 100 per PgBouncer instance.
- **Default Pool Size:** 20.
- **DB Connection String:** postgresql://user:pass@pgbouncer-host:6432/vyaparnet?pgbouncer=true

## 4. SEARCH ENGINEERING

### 4.1 Full Text Search (FTS) Deep Dive

**Implementation:**
1. **Extension:** pg_trgm (for fuzzy search) and unaccent (for normalization).
2. **Column:** searchVector (tsvector) on Product, Category.
3. **Trigger:** Auto-updates searchVector on INSERT or UPDATE of name or description.

**Prisma Migration Example:**
```sql
-- Add search vector column
ALTER TABLE "Product" ADD COLUMN "searchVector" tsvector;
-- Create GIN index
CREATE INDEX idx_product_search ON "Product" USING GIN (searchVector);
-- Create trigger function
CREATE OR REPLACE FUNCTION product_search_update() RETURNS trigger AS $$
BEGIN
  NEW."searchVector" := to_tsvector('english', coalesce(NEW.name, '') || ' ' || coalesce(NEW.description, ''));
  RETURN NEW;
END
$$ LANGUAGE plpgsql;
-- Attach trigger
CREATE TRIGGER product_search_trigger
BEFORE INSERT OR UPDATE ON "Product"
FOR EACH ROW EXECUTE FUNCTION product_search_update();
```

### 4.2 Search Architecture Spec (Revisited)

- **MVP (Now):** PostgreSQL tsvector + GIN + pg_trgm for fuzzy match.
- **V2 (Next):** Swap to OpenSearch or Typesense for advanced ranking, facets, and analytics.
- **Pattern:** Use a clean repository pattern. The SearchService interface has two implementations: PostgresSearchService and OpenSearchService. Switch via environment variable.

**Hindi/English & Synonym Handling:**
- Pre-load a synonym dictionary (e.g., "kurtee", "kurta set" -> "kurti").
- Use the simple dictionary for tsvector to avoid English-specific stemming on Hinglish words.
- unaccent extension to normalize accented characters.

## 6. OPERATIONAL RELIABILITY

### 6.1 Disaster Recovery (DR)

**Strategy:**
- **Backup Frequency:** Daily automated snapshots (RDS). Point-in-time recovery (PITR) enabled for last 35 days.
- **Cross-Region Replication:** Asynchronous read replica in a different AWS region (e.g., Mumbai ap-south-1 -> Singapore ap-southeast-1).
- **Restore Testing:** Quarterly DR drills. Test restoring the DB from a snapshot to a new instance and verify application connectivity.

| Metric | Target | Reality Check |
| :--- | :--- | :--- |
| **RPO (Recovery Point Objective)** | < 1 hour | Daily backups + PITR |
| **RTO (Recovery Time Objective)** | < 4 hours | Manual failover |

### 6.2 Data Retention Policies

| **Data Type** | **Production** | **Staging** | **Archive** |
| :--- | :--- | :--- | :--- |
| Orders | 7 years | 30 days | S3 Glacier |
| Audit Logs | 2 years | 7 days | S3 Glacier |
| Notifications | 30 days | 7 days | Deleted |
| OTP / Temp | 15 minutes | Immediate | Deleted |
| Session Tokens | 7 days (Redis TTL) | 1 day | Deleted |
| Product Images | Permanent | Permanent | S3 IA |

**Enforcement:**
- Automated Prisma cron jobs for hard-deletion (after soft delete period).
- pg_cron extension for periodic cleanup tasks.

### 6.3 Background Job Governance (BullMQ)

- **Queue Namespacing:** bullmq:prod:order-processing, bullmq:prod:email-sending.
- **Retry Logic:**
  - **Linear:** Retry 3 times (1 min apart) for transient errors.
  - **Exponential Backoff:** For DB/External API failures (2, 4, 8, 16, 32 seconds).
  - **Max Retries:** 5. After that, move to Dead Letter Queue (DLQ).
- **DLQ (Dead Letter Queue):** Jobs that fail after max retries are moved here for manual inspection.
- **Stuck-Job Cleanup:** Cron job to clean jobs stuck in active state for > 30 mins.
- **Job Observability:** BullMQ Dashboard (Exposed via a protected NestJS route).

### 6.4 Schema Migration Governance

- **Tool:** Prisma Migrations.
- **Rules:**
  1. **Backward-Compatible:** Never drop a column that the old app version is using. Add column in one deploy, remove in the next.
  2. **Zero-Downtime:** Run migrations before deploying the new app code.
  3. **Rollback:** Every migration must be reversible. Keep a down migration script.
  4. **Pre-Deployment Check:** prisma migrate validate and prisma migrate diff in CI.
  5. **Environment Isolation:** Never run prisma migrate dev in production. Use prisma migrate deploy.

### 6.5 API Deprecation Policy

- **Versioning:** /api/v1/..., /api/v2/... in URL path.
- **Deprecation Timeline:**
  - New API version released.
  - Old version supported for 6 months.
  - Sunset header returned with every old API response (Sunset: <date>).
  - After 6 months, old version returns 410 Gone.

## 7. SECURITY & COMPLIANCE

### 7.1 Data Encryption

- **In Transit (Data-in-motion):**
  - TLS 1.2+ mandatory for ALL external traffic (ALB, CloudFront).
  - mTLS (Mutual TLS) for service-to-service communication inside the VPC (ECS to RDS, ECS to Redis).
- **At Rest (Data-at-rest):**
  - RDS: AWS KMS encryption (AES-256) enabled by default.
  - S3: Server-side encryption (SSE-S3 or SSE-KMS) for all buckets.
  - ElastiCache: Encryption in transit (TLS) and at rest (KMS) enabled.
  - Backups: Encrypted. Same KMS key as the primary DB.

### 7.2 RBAC (Role-Based Access Control) Deep Dive

- **Granularity:** Roles are NOT just BUYER, SELLER, ADMIN.
- **Permissions:** Permissions are defined as resource:action (e.g., order:create, product:delete, inventory:update).
- **Middleware:** A global NestJS Guard checks permissions from the JWT token against the requested resource/action.
- **Dynamic Roles:** A seller can have a SELLER_MANAGER role that can delegate order:view to a sub-account but NOT product:delete.

### 7.3 Fraud Engine Placeholder (Future V2/V3)

> B2B fraud is a reality. We MUST have a structural placeholder now, even if the ML model comes later.

**Integration Points:**
1. **Order Placement:** Trigger a FraudCheck job via BullMQ. If fraudScore > 0.8, flag the order for manual review before confirming.
2. **Seller Onboarding:** After KYC, run a SellerTrustScore calculation based on business age, GST history, and initial order volume.
3. **Payment:** Flag transactions > Rs. 50,000 for dual verification (OTP + Whatsapp notification).
4. **Returns:** If a buyer's return rate > 20% in a month, flag future returns for inspection.
5. **Operator Collusion:** Monitor patterns where an admin user and a specific seller have anomalous activity correlation (e.g., frequent approval changes).

## 8. SYSTEM FAILURE PHILOSOPHY: "DEGRADE, DON'T DIE"

### 8.1 Failure & Recovery Playbook

**Scenario Handling:**
1. **Payment Gateway Down:**
   - **Impact:** New checkouts fail.
   - **Action:** Circuit breaker trips. Queue payments for retry. Allow "Pay on Delivery (COD)" or "Pay Later" options. Alert Ops team.
2. **DB Slow / Read Replica Down:**
   - **Impact:** Read queries timeout.
   - **Action:** Fall back to Primary DB for reads (increases load, but maintains service). Disable heavy analytics. Alert Ops team.
3. **Queue Backlog (BullMQ):**
   - **Impact:** Notifications, order confirmations delayed.
   - **Action:** Scale background worker containers. If Redis is full, drop non-critical jobs (e.g., "Product Viewed" events) and alert.
4. **Redis Unavailable:**
   - **Impact:** Cache misses. API becomes slow.
   - **Action:** API falls back to DB for every read. Rate-limit aggressive endpoints to protect the DB. Alert Ops team.
5. **WhatsApp API Failure:**
   - **Impact:** OTP and notification delivery fails.
   - **Action:** Fall back to SMS (if available). If both fail, show in-app notification. Alert Ops team.
6. **Search Degraded (FTS issues):**
   - **Impact:** Search results are slow.
   - **Action:** Fall back to simple ILIKE '%term%' on product names. Show static "Trending" categories. Alert Ops team.

### 8.2 Graceful Degradation Matrix

| Component | Healthy | Degraded | Failed | Recovery |
| :--- | :--- | :--- | :--- | :--- |
| **Payment Gateway** | Process payments | Queue for retry | Block checkout, allow "Pay Later" | Circuit breaker + Retry |
| **Search (FTS)** | Fast, ranked results | Simple ILIKE search | Static "Trending" categories | Rebuild index / Fallback |
| **Recommendations** | Personalized | Generic top sellers | Hide section | Cache warm-up |
| **Notifications** | Real-time push | Delayed by 5-10 min | Batch in background | Drain queue |
