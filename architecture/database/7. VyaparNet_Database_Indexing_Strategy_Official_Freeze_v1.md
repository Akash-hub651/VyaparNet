## 1. EXECUTIVE SUMMARY

This document serves as the single source of truth for all database indexing, query optimization, and performance hardening decisions for the VyaparNet B2B Commerce Platform.

**Core Philosophy:**
> **"We do not index tables. We index queries."

Every index must justify its existence by optimizing a real, hot, or critical business workflow.

**Version History:**
- v0.1: Initial schema + basic indexes
- v0.9: Complete 40-step indexing strategy
- **v1.0: Official Freeze (Operational Hardening Applied)**

## 2. INDEX PRIORITY TIERS

| Tier | Meaning | Action on Tier |
| :--- | :--- | :--- |
| **Tier 1** | Must always exist | Zero downtime, monitored, never removed unless replaced |
| **Tier 2** | Important | Monitored, can be optimized but not removed without testing |
| **Tier 3** | Optional / Analytics | Monitored for usage, candidates for retirement if unused > 90 days |
| **Tier 4** | Experimental | Created for specific features, auto-removed after 30 days if unused |

## 6. COMPOSITE INDEX PLAN (Per Domain)

### 6.1 User & Identity Domain

**`User` Table:**
```sql
-- Tier 1: Login via phone
CREATE UNIQUE INDEX idx_user_phone ON "User"(phone) WHERE isDeleted = false;

-- Tier 2: Admin filtering by role and segment
CREATE INDEX idx_user_seg_role_del ON "User"(segment, role, isDeleted);
```

**`Business` Table:**
```sql
-- Tier 1: Seller catalog view
CREATE INDEX idx_biz_owner ON "Business"(ownerId);

-- Tier 2: Segment filtering for marketplace
CREATE INDEX idx_biz_seg_del ON "Business"(segment, isDeleted) WHERE isDeleted = false;
```

### 6.2 Product & Catalog Domain

**`Product` Table:**
```sql
-- Tier 1: Marketplace browsing
CREATE INDEX idx_prod_seg_cat_act ON "Product"(segment, categoryId, isActive) WHERE isDeleted = false;

-- Tier 1: Seller product listing
CREATE INDEX idx_prod_biz_act ON "Product"(businessId, isActive) WHERE isDeleted = false;

-- Tier 1: Full Text Search (GIN)
CREATE INDEX idx_prod_search_vector ON "Product" USING GIN (search_vector) WHERE isDeleted = false;
```

### 6.3 Inventory Domain (Most Dangerous)

**`Inventory` Table:**
```sql
-- Tier 1: Stock check on order placement
CREATE INDEX idx_inv_prod ON "Inventory"(productId);

-- Tier 2: Low stock alerts for sellers
CREATE INDEX idx_inv_biz_low ON "Inventory"(businessId, isLowStock) WHERE isLowStock = true;
```

### 6.4 Cart Domain

**`Cart` Table:**
```sql
-- Tier 2: Find or create user cart
CREATE UNIQUE INDEX idx_cart_user_seg_stat ON "Cart"(userId, segment, status) WHERE status = 'ACTIVE';
```

### 6.5 Order & Fulfillment Domain

**`Order` Table:**
```sql
-- Tier 1: Buyer order history
CREATE INDEX idx_order_buyer_stat ON "Order"(buyerId, status, createdAt DESC) WHERE isDeleted = false;

-- Tier 1: Seller order dashboard
CREATE INDEX idx_order_seller_stat ON "Order"(sellerId, status, createdAt DESC) WHERE isDeleted = false;
```

### 6.6 Payment Domain

**`Payment` Table:**
```sql
-- Tier 1: Payment status polling on checkout
CREATE INDEX idx_pay_order_stat ON "Payment"(orderId, status);

-- Tier 1: Duplicate prevention check
CREATE UNIQUE INDEX idx_pay_idem_key ON "Payment"(idempotencyKey) WHERE idempotencyKey IS NOT NULL;
```

### 6.7 Event Outbox

**`EventOutbox` Table:**
```sql
-- Tier 1: Background job polling
CREATE INDEX idx_eob_stat_retry ON "EventOutbox"(status, retryCount, createdAt) WHERE status IN ('PENDING', 'RETRYING');
```

## 7. FULL-TEXT SEARCH STRATEGY

### 7.1 Native PostgreSQL (MVP)
Used for product name, description, and category browsing.

```sql
-- Setup extensions (one-time)
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS unaccent;

-- GIN index on tsvector (CRITICAL)
CREATE INDEX idx_prod_search_vector ON "Product" USING GIN (search_vector) WHERE isDeleted = false;

-- Fuzzy search for typos (Hinglish support)
CREATE INDEX idx_prod_name_trgm ON "Product" USING GIN (name gin_trgm_ops) WHERE isDeleted = false;
```

### 7.2 Hybrid Search Architecture
- The `SearchProductDocument` model acts as a sync table.
- A background job (`SearchReindexJob`) pushes data to OpenSearch.
- **Fallback:** If OpenSearch is down, application falls back to PostgreSQL `search_vector` GIN index (guaranteed by SLA).

## 8. PARTIAL & COVERING INDEXES

### 8.1 Partial Indexes (Exclude Soft-Deleted Data)
```sql
-- Example on Product
CREATE INDEX idx_prod_active ON "Product"(segment, categoryId, isActive) WHERE isDeleted = false;
```

### 8.2 Covering Indexes (INCLUDE)
```sql
-- Admin Exception Center (only needs id, status, priority, createdAt)
CREATE INDEX idx_st_except ON "SupportTicket"(status, priority, createdAt DESC)
INCLUDE (id, subject) WHERE status = 'OPEN';
```

## 9. PAGINATION STRATEGY (Cursor-Based)

All list queries must use an index on (createdAt DESC, id):

```sql
-- Fetch next page after a specific order
SELECT * FROM "Order"
WHERE (createdAt, id) < ('2025-05-22T10:00:00Z', 'last-order-id')
AND buyerId = 'buyer-123'
ORDER BY createdAt DESC, id DESC
LIMIT 20;
```

**Required Index:**
```sql
CREATE INDEX idx_order_buyer_cursor ON "Order"(buyerId, createdAt DESC, id DESC);
```

## 10. PARTITION-AWARE INDEXING

Tables designated for partitioning (`Order`, `AuditLog`, `EventOutbox`) will have indexes **recreated per partition**:

```sql
-- Example for monthly partition 'orders_2025_05'
CREATE INDEX idx_orders_2025_05_buyer ON orders_2025_05(buyerId, status);
```

## 11. SLOW QUERY SLA (Service Level Agreement)

| Query | p95 Latency Target | p95 Latency Critical |
| :--- | :--- | :--- |
| Product Search | < 150ms | > 300ms (Alert) |
| Buyer Order Listing | < 100ms | > 250ms (Alert) |
| Seller Order Listing | < 100ms | > 250ms (Alert) |
| Inventory Lookup | < 50ms | > 100ms (Alert) |
| Cart Operations | < 50ms | > 100ms (Alert) |
| Payment Status Check | < 50ms | > 100ms (Alert) |
| Notification Count | < 30ms | > 80ms (Alert) |
| Admin Dashboard | < 500ms | > 1s (Alert) |
| Background Job Poll | < 100ms | > 200ms (Alert) |

**Enforcement:** Queries exceeding p95 critical threshold are automatically flagged in Grafana for review.

## 12. HOT TABLE WRITE STRATEGY

**Inventory, Payment, EventOutbox** are high-write tables.

### 12.1 Write Amplification Mitigation
1. **Batch Updates:** Group inventory movements. Avoid N+1 updates.
2. **Batch Inserts:** EventOutbox entries inserted in batches of 100.
3. **Partitioning:** Monthly partitions prevent single-table bloat.
4. **Partial Indexes:** Only index active rows.
5. **Async Processing:** Inventory reservation cleanup runs in background workers.

---

## 13. DEADLOCK DETECTION & RETRY STRATEGY

### 13.1 Deadlock Prone Areas
- **Inventory:** Concurrent `UPDATE` on quantity + reservedQty.
- **Payment:** Duplicate `UPDATE` on status.

### 13.2 Strategy
1. **Explicit Locking:** Use `SELECT ... FOR UPDATE` on inventory rows in a deterministic order.
2. **Retry Logic:** Exponential backoff (2s, 4s, 8s, 16s).
3. **Timeout:** Set `lock_timeout = '2s'` in Prisma connection string.
4. **Monitoring:** Log all deadlocks to `SecurityEvent` table.
5. **Alerting:** Alert if deadlocks > 5 per minute.

---

## 14. INDEX RETIREMENT POLICY

1. **Audit:** Run weekly `pg_stat_user_indexes` check.
2. **Flagging:** Any index with `idx_scan = 0` for > 90 days is flagged.
3. **Review:** Flagged indexes are discussed in the weekly engineering sync.
4. **Removal:** If no objections, `DROP INDEX CONCURRENTLY` in the next maintenance window.
5. **Rollback:** Before dropping, rename to `_deprecated` for 7 days.

## 16. QUERY GOVERNANCE RULES

### 16.1 Forbidden Query Patterns
- **Full Table Scans** on tables > 10,000 rows without `WHERE` clause.
- **`SELECT *`** in production APIs (always select specific columns).
- **Cartesian Joins** (missing join conditions).
- **`OFFSET > 1000`** (use cursor-based pagination).
- **Unbounded `IN` queries** (e.g., `WHERE id IN (...1000 items...)`).

### 16.2 Maximum Joins
- **API Queries:** Max 4 joins per query.
- **Dashboard Queries:** Max 6 joins per query. Use denormalized reads if exceeded.

### 16.3 CTEs (Common Table Expressions)
- Materialized CTEs (`WITH ... AS MATERIALIZED`) allowed in Postgres 12+ for complex reports.
- Standard CTEs (non-materialized) if execution time < 50ms.

## 18. HINGLISH NORMALIZATION STRATEGY

### 18.1 Problem
Users search for:
- `kurti`, `kurtee`, `kurta set` -> should all match `kurti`.

### 18.2 Solution
1. **Synonym Dictionary:** Pre-load common Hinglish variations into a `SearchSynonym` table.
2. **`unaccent` Extension:** Normalize accents.
3. **`pg_trgm`:** Fuzzy match for transcriptions.
4. **Future:** Custom `normalization` service that expands Hinglish queries into standard English before hitting search index.

## 20. CONNECTION POOL TUNING (PgBouncer)

### 20.1 Configuration
- **Pool Mode:** Transaction Pooling
- **Max Client Conn:** 100 per PgBouncer instance
- **Default Pool Size:** 20
- **DB Connection String:** `postgresql://user:pass@pgbouncer-host:6432/vyaparnet?pgbouncer=true`

### 20.2 PgBouncer + Index Heavy Workload
- **Read Queries:** Directly via Read Replicas (bypass PgBouncer for heavy analytics).
- **Write Queries:** PgBouncer handles write pooling for `Order`, `Payment`, `Inventory`.

---

## 21. FAILOVER QUERY STRATEGY

### 21.1 Read Replica Unavailable
- **Action:** Fallback to Primary DB for reads.
- **Mitigation:** Reduce cache TTL to 15 seconds to compensate.

### 21.2 Search (OpenSearch) Unavailable
- **Action:** Fallback to PostgreSQL `search_vector` GIN index (returns `ILIKE` fuzzy results).
- **Graceful Degradation:** Show "Trending Now" static results if both fail.

### 21.3 Primary DB Unavailable
- **Action:** Return `503 Service Unavailable` for mutable operations.
- **Read-only mode:** Serve cached data for product listings if Redis is up.

## 22. MONITORING, BLOAT & MAINTENANCE

### 22.1 Autovacuum Tuning (PostgreSQL)
```sql
ALTER TABLE "Inventory" SET (autovacuum_vacuum_scale_factor = 0.05);
ALTER TABLE "Payment" SET (autovacuum_vacuum_scale_factor = 0.05);
ALTER TABLE "EventOutbox" SET (autovacuum_vacuum_scale_factor = 0.02);
```

### 22.2 Reindex Policy
- **Quarterly:** Run `REINDEX INDEX CONCURRENTLY` for Tier 1 indexes on a maintenance window.
- **Trigger:** If `pg_stat_user_indexes` shows `idx_scan = 0` and `pg_size_pretty > 100MB`.

### 22.3 Monitor Index Usage
```sql
SELECT indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY idx_scan ASC;
```

## 23. MIGRATION SAFETY PLAN

1. **Zero-Downtime Index Creation:** Always use `CREATE INDEX CONCURRENTLY`.
2. **Staging Testing:** Replay production queries and measure execution plans.
3. **Rollback Plan:** Keep old indexes for 7 days before dropping if new indexes fail.
4. **Metrics Comparison:** Compare `pg_stat_user_indexes` before and after.

## 24. SUMMARY OF INDEX CHECKS BEFORE DEPLOYMENT

Before every release, ask:
1. Does this feature require a new index? (If yes, which query?)
2. Is the index partial (to exclude soft-deleted rows)?
3. Is a covering index `INCLUDE` possible for dashboard reads?
4. Is `CONCURRENTLY` used for zero-downtime creation?
5. Has `EXPLAIN ANALYZE` confirmed the index is being used?
6. Does this index negatively impact write-heavy tables?
7. Is the index added to the Read Replica too?
8. Does the new query violate the **Slow Query SLA**?
9. Are deadlocks possible with `FOR UPDATE`? Is a retry strategy defined?
10. Is cache invalidation logic defined for this new data pattern?
